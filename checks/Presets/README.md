# Preset Numeric Checks

Run `dotnet run --project checks/Presets/PresetsChecks.csproj -c Release` from the repository root. No game process, save, Unity objects, or live automation is used.

The original identity/replay/sequence suite remains in `Program.cs`. `NumericChecks.cs` adds independent game-rule fixtures and regression checks for the numeric capture/planner boundary.

The standard `PresetsChecks.csproj` runs fourteen-objective activity, immediate adventure/capacity, and model/schema checks without extra imports. `ActivityChecks.cs` covers actual shared resource allocations, TM/AUG gold, AT target weights, exact extra-lane replay and bounded float forecasts. `AdventureObjectiveChecks.cs` verifies immediate power/toughness, legacy six/ten/twelve-weight compatibility and planned-support/replay array padding. `ModelChecks.cs` covers the current schema and removed legacy horizons. See [numeric activity integration, restrictions and commands](../../docs/preset-activities.md).

The shared runner uses optional partial hooks. `checks/PresetIntegration/NumericIntegrationChecks.csproj` explicitly includes the activity and capacity fixtures; the standard `PresetsChecks` runner includes all fixtures automatically. `ModelChecks.targets` is no longer used.

## Capacity Objectives

Energy Cap (index 12, energy units) and Magic Cap (index 13, magic units) score only projected native **total** capacity, including every raw cap tier and AllCap. Current/idle/reclaimable pools, retained training, power, bars, NGU rates and adventure stats do not contribute to these objective values. Existing legality, retained-training capacity, explicit combat minimums and support funding constraints still determine feasibility. Instant capacity is not reduced by swap downtime or multiplied by horizon; weighted cap requests do not advertise two-phase sequences.

Requested cap specialists run before unrelated specialists, and their raw-cap greedy seeds are retained even after the ordinary search budget expires. The seed considers the best instance per distinct item ID and assigns stronger items to the full-strength hand. The overall constrained/mixed search remains heuristic, not a general global optimum guarantee. Pure cap requests bypass the irrelevant finite-target NGU auto-advance forecast blocker without changing the native preference or allocation execution paths; adding production restores the existing guard.

`CapacityObjectiveChecks.cs` covers massive unrelated/opposite-cap distractors, absent legacy union stats, high-tier/AllCap specs, duplicate instances, offhand order and empty-hand moves, exhaustive dual-wield comparison, frozen normalization/replay, small/empty pools, safety constraints and expired search budgets. The offline native adapter runner's `--capacity-objectives` mode verifies compiled capture/preview/replay against native capacity getters and the native magic unlock boundary (`Magic.capMagic >= 10000`). It never attaches to a running game or changes an installed assembly/save.

## Adventure-Dynamic Policy

`CustomLoadoutPreset.AdventureDynamicWeight` is an optional finite double in [0, 1000000], default zero. Zero is omitted even when present in the original JSON, preserving old serialized identities. All fixed weights may be zero only when the dynamic weight is positive. The twelve objective positions are unchanged.

Runtime interface: `public CustomLoadoutPreset ResolveAdventure(int mode, int zone)`. Pass the already normalized runtime task after rule selection and locked idle-zone fallback, not the raw configured mode/zone. The pure method clones through `ToJson`/`Parse` and adds the full dynamic weight to PP (mode 0 or unknown/default), boosts (mode 2), or zone farming (mode 1), with no extra immediate-power weight. Other fixed goals remain unchanged except for uniform scaling when execution weights exceed the schema maximum, preserving relative objective weights. Only mode 1 copies `zone`; every other supported mode clears it to -1. The returned clone has zero dynamic weight, preventing double addition, and retains support preferences. Mode 3 (max ITOPOD push) and mode 4 (manual adventure) throw `InvalidOperationException` with explicit deferred/unsupported messages. No runtime wiring or game-state normalization is performed here.

`AdventureDynamicChecks.cs` exercises serialization compatibility, validation, additive blends, task resolution, deep-clone isolation, idempotence, real planner consumption and automatic digger preferences through the existing shared coefficients. `checks/PresetLibrary` additionally verifies the sixteen fresh seeds, persisted dynamic edits, clearing to zero, and unchanged historical farming seeds/references.

`StageTargetsNativeChecks.cs` uses `StageTargetsNative.targets` as an alternate entry point for the existing Framework native integration project. It exercises the compiled snapshot stage hook with native menu targets -1, actual AT ticks/completion gates, strict preflight weight/parity checks, and deterministic completed-target replay. Its build/run contract is documented in [numeric preset activities](../../docs/preset-activities.md#focused-checks); no project manifest or live game is changed.

## Empty-Slot Replay

`EmptySlotChecks.cs` reproduces a source-linked search from current `[empty, weapon]` to balanced `[weapon, empty]`, replays the whole preview, and verifies that applying current remains eligible. Empty placeholders retain destination group validity and do not become the current destination occupant.

`EquipmentChecks.csproj` is a separate .NET Framework 4.8 runner. Build it with MSBuild, then run `PresetEquipmentChecks.exe <production-NGUInjector.dll> <game-Managed-directory>`. It invokes the compiled shared exact-map swap planner and executes only the real game's data-only `Inventory` swap methods on isolated fixtures, never native Unity controllers or live game state. Cases cover empty main/offhand and accessory moves, full-inventory current gear, staging failure, and clearing omitted destinations using inventory space freed by the incoming gear.

## Reference Rules

The installed NGU game assemblies were inspected with the existing read-only `ilspycmd` aid. Relevant implementations are `Character.totalEnergyPower`, `totalMagicPower`, `totalCapEnergy`, `totalCapMagic`, `totalAdvAttack`, `totalAdvDefense`, `totalNGUSpeedBonus`, `InventoryController.specBonus`, `cubePower`, `cubeToughness`, `NGUController.progressPerTick`, `NGUMagicController.progressPerTick`, and `AllNGUController.hardCapNormalLevel`.

- Resource projections start from raw base stats and captured factors. They do not invert clamped getters. Energy and magic have different float/double factor order. Capacity uses banker's rounding; power clamps before both potion multipliers.
- Raw equipment specs are summed in game slot order, with offhand scaling, before tier conversion. Resource/NGU/GPS/drop getter checks stay exact. Adventure uses the explicitly bounded binary32 rounding policy below and rejects larger discrepancies or clamp transitions.
- Both effective cube stats depend on candidate base-plus-gear softcaps. Unity's `Mathf.Pow(float, float)` delegates to `(float)Math.Pow`, which the pure projection reproduces.
- Beast Mode triples incoming damage without reducing the displayed toughness getter. All farming fails closed while it is on; NGU/blood-only presets remain eligible, and no mode toggle is performed.
- NGU capture retains the rounded float power/divider/resource prefix, ordered post-level multipliers, and difficulty divisor. The selected track's level ceiling is read from the game, not inferred from the user's target.
- Capped resource sharing uses exact decimal quotient/remainder arithmetic and returns `long` allocations, including the last unit of an Int64-sized budget.
- Actual reclaimable pools, reservations, percentage splits, and applied NGU/blood allocations stay integer throughout. A near-cap pool cannot round up through a double conversion or gain resources when a later phase raises its cap.

## Bounded NGU Integration

Each fixed allocation starts with zero bar progress, matching the declared ignored-partial-bar assumption. A level's cost is the actual number of repeated single-precision progress additions needed to reach one, with overshoot discarded. The tick counter skips constant-ULP runs within floating-point binades, including tie parity and bars that stagnate before completion; it never loops over every game tick.

Tick cost is monotone with level. The integrator partitions level ranges into constant-cost bands or lower/upper cost bounds. Production is the conservative lower bound on completed levels. It returns only when the gap is at most `floor(lower * 0.005)`, so small gains are exact and larger gains are within 0.5 percent of this frozen, zero-initial-bar model. At most 256 bands and 512 binade steps per cost query are allowed. Uncertifiable production is unavailable, not replaced with a midpoint estimate or silently scored as a known weighted goal.

The literal per-tick oracle in the tests is independent of the grouped integrator. Coverage includes the former 250/251 numerator jump, random transitions, ordered controller factors, tiny-progress float accumulation, full seven-day horizons, and captured hardcaps. Two-phase simulations preserve their existing target/cap-shrink semantics and use the same bounded integrator; ignored bar carry and frozen bonus feedback remain model limitations.

Capture and planning share an operation clock. Search stops at 1.8 seconds, sequence exploration at 2.6 seconds, and capture/replay/apply checks a 3-second cooperative deadline. Post-equipment capture does not reset that clock; an overrun after mutation follows the existing consumed-token/partial-application error path. Individual numeric operations also have fixed iteration bounds. These are work/time safeguards, not hard real-time guarantees against OS suspension or a blocking native getter.

## Mixed-Focus Search

`MixedFocusChecks.cs` adds actual E+M accessory sacrifices alongside PP and boosts, weak-multiplier retained-production scoring, support selection, explicit preferences, core-first policy, Gold affordability, lower digger funding for blood, exact replay and floor comparisons. Both numeric manifests run these checks.

Planned support generates at most 64 deduplicated legal policies, not a gear/beard/digger Cartesian product. Full support passes alternate with gear coordinate search using a top-three support beam; every trial rescores actual NGU/blood production, route and magic split. Auto diggers include the previous seed, immediate-only, single-purpose and tilted portfolios at 100/50/25/0 percent of the requested GPS budget. Explicit digger weights keep their eligible IDs, ranking and proportional allocation, but can use less total funding. Explicit beard priority fixes the filtered/capped selection. Default beards preserve `CoreBeards().Where(unlocked).Take(slots)` exactly; only leftover optional slots vary. Optional choices can matter through initial swap cost even though future growth is not forecast. Current-support mode never substitutes support.

Search and numeric operations retain fixed work limits and the shared 1.8/2.6/3-second cooperative clocks. Each support trial counts as an evaluation. Search has a 6,000-trial ceiling; a final bounded current-gear rescore can add up to 64 trials (normally one after exhaustion). Sequence exploration also honors the evaluation ceiling. On exhaustion the baseline retains its best-known support instead of starting another full support pass. Fixed input and work order are deterministic; a wall-clock cutoff can truncate different amounts of work under scheduling pressure.

Afterward, even if search expired, every specialist's item loadout receives a score-only comparison under the original mixed request and frozen denominators. Each loadout compares at most three already-found support selections (current, mixed incumbent, specialist), accepting only selections in the original request's legal support portfolio. Original fixed magic/blood split, route constraints, support preferences and affordability are reevaluated; focus-only split overrides and incompatible support never get copied into Balanced. The current row and frozen reference metadata are not replaced. Tests derive the work ceiling from 6,000 search trials, up to 64 baseline trials, `Keys.Length * 3` final seed trials and `2 * (Keys.Length + 1)` pre-mixed reference trials (6,136 total for fourteen objectives). Unavailable-specialist evaluations also count toward the search budget. The six-goal large-inventory regression independently rescores seeds to bound Balanced from below.

With positive references the score remains `sum(normalizedWeight[g] * production[g] / frozenDenominator[g])`, not improvement-only utility or a product of bonus multipliers. Positive feasible specialist references are unchanged. Missing/zero specialist references alone may use positive feasible original-policy seeds before mixed optimization; replay never replaces them. Current/specialist gear each try at most current and seed support, filtered to the original support portfolio. All seeds use the same provisional specialist denominators. No final mixed result supplies a denominator. `ZeroReferenceChecks` reproduces the weight1000 PP/mandatory-AT mix and checks feasible positive NGU fallback, retained AT funding, PP selection, positive specialist stability, frozen replay, unchanged weights and bounded work. Excluded/completed/unavailable NGU and locked mandatory AT must not fabricate positive references. Late positive output with a still-zero reference receives one unit of scoring utility, at most its own weight; known zero receives zero and unavailable weighted output still blocks scoring.

Response JSON keeps the existing `normalization`, `normalized` and `relativeToCurrent` fields and adds:

- Root `normalizedWeights`, `productionReferences` (`key`, `candidateKey`, `production`) and `scoring` explanation.
- Each candidate/sequence metric: `specialistReferenceKey`, `specialistProduction`, `retainedProduction`, `retainedProductionPercent`, `weightedContribution`.
- Each candidate: `itopodFloor`, also pinned during replay and used verbatim by one-shot route application.

Retained production is `value / originalReferenceProduction`; 0.8 means 80 percent, not a 20-percent improvement. Zero/unavailable references have null retained ratios/percentages, even when positive output earns the bounded unit scoring utility. `normalized` and `weightedContribution` use the same scoring utility as route/split selection and final scores. Ratios may exceed one when mixed search or fresh observations outperform a positive frozen reference. Applied responses retain reference metadata even when specialist candidate rows are omitted. Sequence remains advisory and is not an apply target.

## ITOPOD Boundaries

Read-only native inspection covered `ItopodPerkController.progressGained`, `AdventureController.powerUp`, `verifyItopodInputs`, `PlayerController.baseDamage`, `minDamage`, `idleAttack`, and `EnemyAI.takeDamage`. Capture now includes repeatable floors through `min(maxItopodLevel, highestReached - 1)` plus actual native enemy HP/defense scaled in float order with `1.05f` and the upper 1.02 spawn roll. Floor zero is excluded from stationary routing because native input validation forces the end floor to at least one.

Floor comparison jointly scores captured progress/boosts using conservative minimum 0.8 idle damage rolls, half-defense subtraction and floored damage, allowing at most four hits. Without captured enemy data it compares only the existing one-hit heuristic range and never invents multihit multipliers. Tests cover a PP-rich multihit floor beating the highest one-hit floor, a boost-rich lower floor, nonmonotonic reference rows, exact replay and infeasible pinned floors.

This is still a rate proxy, not a combat simulator: no player HP/death/regen/paralysis simulation, no expected random-roll distribution, no frame/timer simulation, and no pill-expiry or bonus feedback forecast. Planned PP diggers rescale captured native progress and therefore approximate native factor-order/long rounding. Regular-zone safety and hit thresholds and Almanac boost tables remain approximate. No live-game verification is claimed.

Lazy ITOPOD follow-up: native `AdventureController.enemyDeath` calls `activateLazyItopod` after each kill when both `boughtLazyITOPOD` and `lazyITOPODOn` are true. That calls `setOptimalFloor`, overwriting a competing fixed multihit/boost floor. Both flags are now captured and fingerprinted independently, and JSON reports `lazyItopodShifterActive`. With the conjunction active, the planner compares only the native-selected floor for each candidate's projected power, using the native Single prefix and repeatable-floor clamps. Purchased-but-disabled and enabled-but-unpurchased states leave fixed-floor search unchanged. A preference/purchase change between Preview and Apply explicitly rejects before token consumption, pauses, gear/support changes or recalls. Replay never substitutes a new native floor for an incompatible pinned policy; it rejects with a shifter explanation. The final route guard also checks the actual native getter before writing floor inputs.

No shifter preference is changed and no sustained owner is added. One-shot Apply remains one-shot; a later stat change can still move the enabled native shifter's floor. The existing rate/combat approximations remain. Numeric regressions cover the full flag conjunction, incompatible cached policies, native floor zero, and power changes after preview.

## Adventure Precision

The read-only combined report ending `214640-e57ee3ae` recorded adventure power projection `2315574.75` versus native `2315575.25`. Fresh inspection of the installed getter IL confirmed the order: base plus gear plus effective cube, then AT, NGU, NGU2, beard and digger before the first float-local store; subsequent multipliers store the float local individually before the native clamps. The inherited projection instead captured every factor into a `float[]` and explicitly rounded every prefix operation. It also rounded the cube threshold before its comparison. That changes both quantization and near-threshold cube branches; a wider relative tolerance alone would hide those errors.

Capture now preserves getter F results in `double[]`; the numeric projection keeps the prefix through the first five multipliers, then models the float-local stores. The cube threshold comparison retains the base-plus-gear F prefix. Unchanged adventure beard/digger selections use the captured native factors, not the separately rounded shared support values. Actual power/toughness capture materializes the returned Singles explicitly. No clamped total is inverted or used to rescale factors, and shared support code is unchanged. Changed-support alternatives still use the existing shared fixed-level effect projection and its rounding approximation.

Bit-identical agreement for all getter/JIT contexts is not claimed. The near-report fixture produces native power `2315575.25` and now matches exactly, as do 33 adjacent-input references. A controlled multi-slot corpus exercises 1,200 native power/toughness comparisons with non-unit AT/NGU/challenge/perk/hack/wish/card inputs, native beard/digger effects, candidate cube thresholds, Beast Mode and the completed accessory set. In the recorded run, 1,130 cases matched exactly; the remaining deviations were bidirectional and at most four ULPs. A preceding single-weapon corpus reached five ULPs. The complete outer getters and native cube/support arithmetic are not replaced by projection formulas; unrelated multiplier inputs are isolated fixture boundaries.

`AdventureParity` is an adventure-only acceptance policy capped at seven binary32 ULPs, not a universal mathematical error certificate. It rejects nonfinite totals, discrepancies crossing native minimum/maximum clamp endpoints, eight-ULP differences, omitted multipliers and legacy cube/rounding cases outside that cap. Resource/NGU/GPS/drop parity remains exact. Accepted nonzero adventure differences are included in response warnings with both values, so this does not silently hide them. The cap is well below `1e-6` relative for positive normal floats, but is expressed in representable float steps rather than a blanket relative epsilon. Native/JIT versions outside the tested corpus can still fail closed.

Adventure-precision follow-up verification: fresh production Release `Rebuild` passed; both source-linked numeric runners passed 1,580 assertions each; the compiled native adapter runner passed 4,075 assertions, including 1,200 adventure comparisons and 30 complete captures. The final multi-slot corpus measured 1,130 exact results, 28 above and 42 below native, with a four-ULP maximum. No shared support sources, installed game files, saves, UI or live processes were changed.
