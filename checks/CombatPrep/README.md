# Combat Prep Planner Checks

Run from the repository root:

```powershell
dotnet run --project checks/CombatPrep/CombatPrepChecks.csproj
```

This is an offline .NET 8 executable, source-linking the production planner with C# 7.3 enabled. It requires no game assemblies, plugin build, Unity, JSON library, network package, or live save. `System.Text.Json` is used only by the checks to verify the response size, not by the planner. The check executable explicitly enables optimization in both configurations so its CPU assertions measure the optimized planner, not Debug JIT overhead.

## Adapter Contract

All models and the engine are in `NGUInjector/Managers/CombatPrepPlanner.cs`, namespace `NGUInjector.Managers`. Types are `internal` with public DTO properties for the same-assembly Main adapter.

The production `.csproj` uses explicit `Compile` entries and includes `Managers\CombatPrepPlanner.cs`, `Managers\ResourceProjection.cs`, `Managers\ResourceProjectionCapture.cs`, `Managers\ResourceAllocation.cs` and the shared support sources. Normal production `Rebuild` works without temporary source imports. This pure check project source-links the planner and the two numeric-only helpers, not the game adapter.

The strict-order fix does not change DTO fields. Offline checks do not reload a running injector or establish which DLL is currently loaded. Use [current verification](../../docs/AUTOMATION_IMPROVEMENTS.md#completed-verification) for reported build/check results and the separately owned [phase-support live record](../../docs/PHASE_SUPPORT_LIVE_VERIFICATION.md) for live evidence.

- `CombatPrepPlanner.Plan(snapshot, seconds = 7200)` returns `CombatPrepPlanResult`. Invalid captures return `Success=false` with `Error`; the hard maximum is 86400 seconds. Durations quantize to 50 ticks/second and must include a tick.
- `CombatPrepPlanner.Project(snapshot, osId, phases)` evaluates an explicit ordered policy and throws `ArgumentException` on invalid input. It is useful for replaying a selected alternative without running another search.
- `Current` captures actual current totals, caps, power and speed. `Profiles` supplies up to two legal owned projected profiles for each exact goal string: `Augments`, `AT`, `Wandoos`, `NGU`. Current gear is additionally considered for every phase. Keys must be unique, colon-free and at most 128 characters. Exact equipment references remain external metadata in `OwnedGearRefs`; the engine never invents or validates inventory ownership.
- `WandoosAvailable` must explicitly be captured as true for an available, enabled W system in a supported context. Its default is false. Both `Plan` and `Project` reject false rather than forecasting disabled, locked-system or unsupported challenge training; the adapter should also reject unsupported contexts before capture.
- `ReferenceWandoosProfileKey` optionally chooses Current or a captured Wandoos profile for dump-equivalent time. If omitted, the first Wandoos profile is used, otherwise Current when no W profile exists. Every alternative echoes the selected key.
- `BaselineBossAttack` and `BaselineBossDefense` are **unclamped raw inputs** on the fixed final boss loadout/support at current A/W. Capture before the game's 100 minimum, not from its clamped display getter. Both baseline and projection output `max(100, raw * gain)`. For example raw 1 at 22x gain still outputs 100, not 2200. The existing input names are retained; no additional raw/nullable aliases are needed.
- `AllocationRefreshSeconds` defaults to the shared `CombatPrepPlanner.AllocationRefreshSeconds` constant, **0.5 seconds / 25 game ticks**. The backend executor must use the captured cadence (or the shared constant when always default). Values must be positive whole ticks, at most 86400 seconds.
- `PhaseSpecificSupport=false` requires every profile to match `Current.SupportKey`. If true, phase-specific support must already be included in every captured speed/power and net gold rate. Support switching costs are not inferred. The pure engine needs no support-selection model or game references.
- `CombatPrepProfile.NetGoldPerSecond` is an optional signed finite `double?`, bounded in magnitude by `1e300`. Every visited phase, including Current, AT, Augments, Wandoos, NGU and Background, uses that profile's rate. Null falls back to `CombatPrepSnapshot.NetGoldPerSecond`, never to the previously visited profile or Current's override. Explicit zero is a real rate. Old captures with all profile rates omitted retain their exact frozen-income behavior.
- Each policy starts at Current's actual `min(total,cap)` pools. At every positive-duration phase entry, each available pool becomes `min(previousAvailable, profile.Total, profile.Cap)`. Capacity lost by a visited loadout never refills when returning to higher-cap gear. Unvisited profiles and zero-duration phases do not reduce that policy's pools. Capture Current's actual usable totals and each projected profile's own usable totals/caps, **not a global minimum across candidate profiles**. `EndEnergyPool` and `EndMagicPool` report the remaining counts. No refill, future loot, NGU growth or unknown future support is credited.
- Progress is normalized `[0,1)`, levels/counts are nonnegative `long`, and coefficients are finite, nonnegative doubles bounded by `1e300`. Formulas and outputs saturate safely; level additions cannot wrap. `CaptureAssumptions` is limited to 2048 characters and is echoed as a disclosure.
- Current augment and Wandoos formulas must agree with actual current getter totals to relative tolerance `1e-6`. The same accepted formula representation normalizes both the baseline and forecasts, so baseline gain is exactly one.

## Formula Capture

Shared resource projection lives in `ResourceProjection`: the 14-member `ResourceSpec` order is EnergyPower/2/3, MagicPower/2/3, AllPower, EnergyCap/3, MagicCap/3, AllCap, NGU/2. `Project(float[])` preserves native expression order, distinct Energy/Magic capacity precision, minimum/hard caps, post-cap power potions and capacity midpoint-to-even integer rounding. Do not introduce extra intermediate float casts: their additional IL conversions change .NET Framework results even when .NET 8 tests agree. `ResourceFoundationChecks.cs` checks independently transcribed formulas with literal spec indexes; the integration executable additionally compares the installed native getters.

`ResourceAllocation.ShareCapped(long[], long, int[])` is the extracted exact weighted largest-remainder allocator, including index tie-breaking and zero-weight exclusions. `SplitPair(long, long, long, double)` deliberately retains Combat's different policy: floor the second lane's double share, give the integer remainder to the first, then redistribute caps without funding excluded lanes. This includes the historical double rounding at `long.MaxValue`, not a new decimal half-split. Both the pure phase engine and execution call it. Independent BigInteger oracle checks cover extreme weighted products/budgets and input immutability.

AT-3 and AT-4 both consume **energy**, including AT-4's magic-Wandoos-speed training. Capture each controller's `baseTime`, `levelFactor`, current level/progress and optional target. Capture `Character.totalAdvancedTrainingSpeedBonus()` and actual Energy Power for each gear/support profile. The model uses `allocatedE * sqrt(Epower) * ATspeed / (50 * baseTime * (L+1))`, with W speed multiplier `1 + levelFactor * L`.

`FreeAdvancedTraining=true` captures Wish 190. Native `progressPerTick()` returns **1**, not an infinite paid-energy coefficient. After the actual basic-training unlock, `updateAdvancedTraining()` advances each lane once per tick even at zero energy. Crucially, native `hitTarget()` returns false at zero allocation, including disabled (`-1`) and reached positive targets. The planner therefore excludes paid AT phases and advances unlocked free AT lanes in **every** positive-duration phase, including Augments, Wandoos, NGU and Background. `Project` rejects an explicit AT phase in this context rather than inventing a paid target gate. Free AT does not consume either resource; initial partials are discarded on its first completion. W rates use pre-tick free AT levels, a conservative ordering relative to AT-before-W callbacks. Native callback ordering is not a guaranteed Unity scheduling contract. The adapter captures native unlock independent of menu targets in this context, rejects a pending banked-level transfer, and invalidates a captured epoch if Wish 190 activation changes.

Augment lane progress uses `allocatedE * Epower * AugmentSpeedFactor * ProgressCoefficient / (L+1)^LevelExponent`. The inspected IL has exponent **1 for both augment and upgrade progress**. Normal/evil lane coefficients use all actual speed factors divided by `50000 * difficultyLaneDivider`. Sadistic uses its lane divider and `sadisticDivider()`. Capture samples away from the tiny/float-max clamps, divides out sample amount and reference Energy Power, and multiplies by the current `(L+1)`. For upgrades it explicitly uses the existing verified-IL `Extensions.getUpgradeProgressPerTick(controller, amount)` helper: the installed native `getUpgradeProgressPerTick(long amount)` ignores its argument and must not be used as a sample-amount getter. See [the backend overload finding](../../docs/COMBAT_PREP_BACKEND.md#native-upgrade-overload-bug). Projected `AugmentSpeedFactor` is the ratio of all non-Energy-Power speed multipliers to that reference profile, not another copy of power.

Gold is paid at bar **start**. Capture `getBaseAugCost() * Character.augDiscount()` as augment `CostCoefficient`, exponent 1; capture `getBaseUpgradeCost() * augDiscount()` for upgrade, exponent 2. Positive partial progress implies already paid; `Paid=true` can represent an explicitly paid zero-progress bar. The engine charges augment before upgrade, and the active profile's fixed net income accrues once after each tick. Augment affordability waits use that same rate. `GoldSpent` counts augment/upgrade purchases only; recurring expenses are already included in signed `NetGoldPerSecond` and reduce `GoldRemaining` across every phase. Gold floors at zero during losses and saturates at `1e300`; future-phase income cannot fund an earlier unpaid bar. Magic-W overlays add no income because their augment prefix already accrued it. AT checkpoints contribute training/resource deltas, never cached gold: the actual incoming state's bound rate accrues exactly once over its actual phase window.

### Backend Support Integration

The backend now uses one shared `SupportContext` and a support metadata mapping separate from planner DTOs. It supplies distinct current-support and deterministic standard phase-support variants, at most two projected profiles per goal plus the one actual `Current` (original gear AND original support). `SupportKey` is opaque identity; backend metadata resolves it to the exact captured selection for later capture/apply. Shared support effects are baked into each profile's existing numeric factors and nullable net rate; there are no `SupportSelection` or pure-to-game references in the engine. Gross/drain reporting belongs to additive backend JSON, not a pure-engine `SupportSummary`. This is bounded fixed-level comparison, not exhaustive support search or future-growth modeling; see [Combat Prep Backend](../../docs/COMBAT_PREP_BACKEND.md).

Replay/profile validation includes the captured nullable net rate (or its resolved value with the same snapshot fallback) as well as existing numeric/profile/support metadata. Reusing a profile key does not imply that a later capture has the same income. Fresh backend recapture replays cached exact gear/support under fresh DTOs without resizing the selection or mutating a running planner context. All planner caches remain call-local; augment/AT cache keys explicitly include resolved income, and copied states retain their bound rate.

Capture `baseBoost` and `augTierBonus()` for every tier, including existing levels on locked tiers. Actual total is `max(1, (1 + sum(baseBoost * (U^2+1) * A^tierExponent)) * AugmentGlobalFactor)`. The global factor includes actual fixed challenge, NGU and difficulty-nerf multipliers. Do not recover that factor by dividing the current total when the game's final clamp is active.

Wandoos progress is `allocatedResource * speedWithoutAT * (1+ATlevelFactor*ATlevel) * OSspeedFactor * bootupFactor / OSbaseTime`, with **no resource power multiplication**. Profile speed capture must divide out current AT and, if separately modeled, bootup. Capture current-difficulty OS bases from controller getters. `OSFactor()` depends on `OSLimit()`; each OS carries a speed ratio relative to the OS used for profile speed capture.

The OS bonus is represented by coefficient, level offsets and exponents, not an estimated sqrt of dumps. The inspected IL formulas are:

- 98: `((1+E/100)*(1+M/25))^0.8`.
- MEH: `(1+E/5)*(1+2*M)`.
- XL: `((1+6*E)*(1+40*M))^1.0499999523162842`.

The DTO comments explain the equivalent normalized coefficient/offset representation. Both zero levels return 1. Fresh captures can consider unlocked OSes in the current difficulty only. Any existing level, progress or allocated dump forces the current OS; switching is never proposed by silently erasing progress. Switching OS preserves bootup in the inspected game.

The production capture now supplies `WandoosBootupElapsedSeconds`, `WandoosBootupDurationSeconds` and `WandoosBootupCompletionFactor`. Native duration is `3600` or `3240` with the completed XL set, multiplied by `clamp(1 - .1 * evil level-100 challenge completions, .5, 1)`. Speed is `elapsed/duration` before completion, then `1.1f` with the completed Wandoos set, otherwise `1`. The completion bonus is a discontinuity, not an extra multiplier throughout the ramp. The shared clock advances during all phases, independently of dumps, and is preserved on OS changes. Production captures require installed and enabled Wandoos; installation is not modeled.

Profile W coefficients exclude **both** AT and bootup. Capture directly transcribes `Character.totalWandoos{Energy,Magic}Speed`, substitutes only owned gear and shared support, and parity-checks Current against native getters. It never divides a zero live speed to recover a coefficient. Future owned W gear can therefore train after a fresh zero boot without inventing future equipment or growth. Duration zero retains the existing explicit profile early/late model for supplied pure snapshots; production does not use that approximation.

Native progress is sampled before `advanceBootup()` on each 50-Hz tick. Varying rates use refresh-held allocations and individual tick completions; full-boot constant segments still batch directly. Windows split at boot completion and free-AT saturation without prematurely refreshing the allocation. The engine uses double clock/formula arithmetic, not bit-identical Unity float rounding or `PlayerTime.advanceTime(.02f)` drift. Each completion discards overflow and grants at most one level per tick. Rates at or below `1e-9` make no progress.

## Search And Execution

The search scores at most 1440 complete policies (at most **1380** in the maximum paid-AT 7-tier/3-OS/2-projected-profiles-per-goal shape), caches augment prefixes and AT checkpoints within one call, and batches constant Wandoos progress directly. The counter includes complete evaluations before alternative deduplication; exceeding the bound fails explicitly, never silently drops later families. Checkpoints preserve held allocations and their refresh remainder; AT cache keys include the effective incoming energy **and** magic pools, as well as profile and split. The augment-prefix cache explicitly keys `BackgroundMagicWandoos=false`; true magic-W overlays are calculated on copies and never contaminate background-free prefixes. It searches every unlocked augment tier at coarse duration fractions before using exact same-profile/time tier dominance. It is not a globally optimal schedule solver.

Families are full augments (optionally budgeted magic W), W without AT, AT then W, augments then W, augments then AT then W, augments then NGU with background W, background-only, **AT then Augments with budgeted magic W then W**, and **AT then Augments with budgeted magic W then NGU background**. The last two have family keys `ATThenAugmentsWandoos` and `ATThenAugmentsNGUBackground` and use the same existing phase DTOs.

The broad families retain `.125`, `.25`, `.5`, `.75` time fractions and AT weights `0`, `.25`, `.5`, `.75`, `1`. Joint refinements shortlist one AT gear profile from the OS's broad AT-then-W results and two distinct actual augment-gear/tier choices from **background-free** augments-then-W results. Augments -> AT -> W uses the best one of those background-free prefixes, `.125`/`.25` of remaining time for AT, and all five weights. AT-first seeds retain both augment choices and three paired timings (AT `.025`/`.125`/`.25`, then Augments `.75`/`.5`/`.25` of the remainder), now at equal AT weights to reserve budget for adaptive timing.

Each OS then refines its best policy in six families: AT/W, Augments/W, Augments/NGU-background, Augments/AT/W, AT/Augments/W, and AT/Augments/NGU-background. It tries moving each internal boundary in both directions by horizon `/16`, `/64`, `/256`, rounded up to the allocation cadence. Each scale recenters on the best result from the previous scale. At most **54** complete policies per OS are added; nonpositive phases are skipped, not extended. Gear/support, AT weights, augment tier and background permission remain fixed locally; every candidate resimulates the actual ordered phases and recomputes level targets. This is coordinate refinement around shortlisted schedules, not exhaustive tier/weight/time optimization. Every AT-first augment forecast uses actual earlier AT, income and policy-local pool depletion.

Up to 12 diverse alternatives include each available semantically distinct family winner and the current snapshot baseline. Deduplication happens **before** selecting family winners and the top 12. Its identity is OS plus ordered executable phase fields, targets/weights/budgets and actual slot-aware `OwnedGearRefs` with captured support, not `GearProfileKey`, `GearGoal`, labels or family aliases. Gear-reference enumeration order is canonicalized; references must identify the actual slot/item instances. Equivalent Current/goal aliases occupy one choice, while genuinely different equipment, support or phase policies remain distinct even with identical gains. The objective is actual end augment total times actual W bonus. Boss attack/defense scale the caller's **raw unclamped** fixed final-loadout/support inputs and then apply the 100 floor, never scale an already-clamped getter or the prep loadout's combat stats.

Returned phases carry gear goal/key, duration budget, augment tier and projected augment/upgrade targets, explicit AT energy-lane weight, projected AT-3/4 targets, and background resource policy. Execution must reproduce capped equal sharing for augment pairs and capped weighted sharing for AT, excluding zero-weight lanes. It must never fund **either** W lane before **any later AT**, or during AT. This includes magic W during an augment prefix. Augments preceding AT always have `BackgroundMagicWandoos=false`; no joint-policy W work can be moved in front of the last AT gate. AT -> Augments may enable budgeted magic W only after both planned AT targets have completed. If late, unfinished augment/AT targets gate phase advancement; the original global deadline must never extend. The engine does not execute phases or mutate game targets.

`Project` permits at most one AT and one Augments phase in either order, followed by at most one terminal Wandoos/NGU/Background phase. It rejects repeats, terminal-before-prep ordering, AT background permission, and any earlier augment magic-W permission followed by AT (even if the current magic pool is zero). Existing mid-rebirth W levels, partials and allocations are baseline state, not newly scheduled W work: they are preserved, and allocations are recalled during AT, without resetting progress or demanding a fresh rebirth.

AT/augment capped shares are allocated at phase entry and then **held unchanged for 25 ticks** at the default cadence. Rates still decrease with the current level, gold is still paid on each actual bar start, and completions still discard overflow; completions do **not** immediately recap or redistribute resources. Already-allocated augment lanes may resume on income during a hold; an excluded lane waits for the next refresh. Gold-starved or target-completed allocations remain occupied until refresh. AT target bounds are checked when allocating at refresh, not during the hold, matching unlimited game menu targets: an allocation can overshoot a level target before its next refresh.

Phase transitions are observed on refresh boundaries. `Project` rounds cumulative scheduled deadlines to the next refresh without resetting the original absolute horizon; lateness consumes later phase budgets, and zero remaining budget cannot enter a loadout, bind its income or start W. Gold accrues under the actual phase's profile for the entire observed window, not under nominal-duration or future-phase rates. Returned phase durations describe those actual observed windows and replay directly. For example an AT budget of .1s followed by W .4s under a .5s global deadline trains only AT and accrues only AT income, never grants .4s of impossible W work. Ideal captured cadence is modeled, not real Unity scheduling jitter or missed refreshes.

The inspected adapter uses exact `ceil(1/unit)` AT caps without a safety multiplier, and binary-searches real augment amount getters for the smallest one-tick allocation. The pure engine uses double coefficient formulas and exact integer sharing/ceil caps; it does not add a `1.000002` buffer. Residual live amount-getter float rounding remains part of capture/live verification, not a reason to assume a higher initial AT cap.

Background W has independent snapshot budgets: `BackgroundEnergyFraction = .03` and `BackgroundMagicFraction = .03`. Each permitted lane uses `floor(min(total,cap)*itsFraction)`, then caps at one tick per bar. Returned phases carry separate `EnergyResourceFraction` and `MagicResourceFraction`; background fractions cannot exceed the corresponding snapshot budgets, including explicit `Project` policies. During augment phases only magic can background W, and never when a later AT is planned; energy remains the augment pair's full capped sharing budget. Ordinary `Wandoos` phases can use full pools. AT funds neither W lane, preserves existing W partials, and ends with both W allocations zero.

All capped leftovers are reported as NGU resource-seconds, with no invented NGU growth. End W levels, allocations, progress, all augment levels/progress/paid flags, AT levels/progress, gold remaining/spent and separate equivalent-time metrics are returned.

Input DTOs must not be mutated concurrently with a call. The planner never mutates inputs, and no caches survive the call.

## Equivalent Times

`EnergyFocusEquivalentSeconds` and `MagicFocusEquivalentSeconds` are **W dump-equivalent training times**, not resource-allocation costs. Each equals its completed W level gain from the snapshot divided by its own reference full-focus W dumps/second. Existing levels are subtracted; partial-progress changes are reported separately and do not count as completed dumps.

Reference rates use `ReferenceWandoosProfileKey`, the alternative's selected OS and speed ratio, its **final AT-3/4 levels**, and the reference profile's bootup factor at prep end. They respect the reference profile's usable pool, the policy's remaining pool after all visited gear, and the W cap: switching to reference gear cannot refill lost resources. If capped per-tick progress is `q > 1e-9`, steady-state dump rate is `50 / max(1, ceil(1/q))`, not `50*q`: completion overflow is discarded and the maximum is 50 dumps/second per lane. They are exposed as `EnergyReferenceDumpsPerSecond` and `MagicReferenceDumpsPerSecond`.

A zero pool, zero/tiny speed or saturated `long.MaxValue` level yields reference rate zero. That lane returns equivalent seconds zero with `EnergyFocusEquivalentKnown=false` or `MagicFocusEquivalentKnown=false`; consumers must check the flag instead of treating that zero as a measured duration. Baseline gains are zero, even when its reference rate is known. These steady-state equivalents are not an exact replay duration for the snapshot's starting partial bars.

`ResourceFocusEquivalentSeconds` is a distinct **resource-allocation opportunity-cost metric**, summing prep resource-seconds divided by each reference full-focus allocation. It is not W dump training time and should not be displayed as such. Zero explicit allocation denominators default to the selected NGU profile's usable pools; both default and explicit counts are limited by that profile's usable pools and the policy's remaining pools. `ResourceFocusCostKnown=false` reports an unavailable required denominator. A missing NGU allocation reference does not invalidate W dump-equivalent seconds. No compatibility aliases are provided for the initial contract.

Additive outputs `EnergyResourceFocusEquivalentSeconds`, `MagicResourceFocusEquivalentSeconds`, `EnergyResourceFocusCostKnown`, `MagicResourceFocusCostKnown` separate those allocation opportunity costs by lane. Their sum equals the existing total; the combined known flag is the conjunction. An unspent lane with zero denominator is known zero, while a spent lane with no reference denominator is unknown zero. `ResourceReferenceProfileKey` names the first captured NGU profile, or Current fallback, used for the denominators. These are planner data only: manual backend/UI serialization must opt into the new fields separately.

## Verification Scope

Fixed checks cover tick overflow, saved progress, tiny rates, bootup splits, actual 98/MEH/XL formulas, raw boss-floor scaling, gold-at-start and already-paid partials, quadratic upgrade cost, generic captured progress exponents, shared augment caps, actual all-tier product/global factor, AT energy-only funding, zero/one and strictly-best 25/75 weights, refresh-observed targets, no W before later AT or during AT, valid AT-first augments, OS unlock/difficulty/freshness guards, system availability, support profiles, baseline parity, policy replay, bounded family diversity/payload, gear-aware alternative deduplication, resource conservation, long saturation, numeric extremes, call-local cache safety and input immutability. Follow-up checks independently verify six AT levels (not 25) under the initial half-second cap-one hold, held/starved augment allocations, cumulative phase-boundary rounding, independent candidate pools, irreversible visited-loadout cap loss, pool-aware checkpoint replay, split background budgets, tick-rounded reference dump rates at final AT/end bootup, zero-rate flags, separation from resource opportunity cost, gold purchases versus recurring expenses, preserved initial W partials during AT and AT -> augment-background -> W partial/allocation/cost accounting. Randomized independent **per-tick, refresh-held** references cover AT and gold-limited augment pairs at default and non-default whole-tick cadences; W has a separate per-tick reference. Non-binary rounding-edge drift is explicitly outside bit-identical claims.

The executable measures a realistic-scale 7200-second snapshot with seven tiers, three native normal-difficulty OS curves and five gear profiles, then repeats with committed W allocations and the current OS only. It also measures nine-profile maximum shapes at 900/3600/7200/86400 seconds and fresh-zero native bootup with paid and free AT. Adaptive evaluation counts depend on valid positive phase boundaries and may vary with horizon. The CPU limit is 2000ms through two hours, scaled linearly to 24000ms for 24 hours. These are offline process-CPU checks, not Unity/Mono scheduling or capture-overhead guarantees. Use the Release command above for optimized measurements.

`NativeProgressionChecks.cs` adds an independent per-tick native ramp/free-AT oracle with initial partials, unlocks, target independence, both resource lanes, nondefault refresh cadence and held resource costs; fresh-zero allocation recovery; free-AT phase exclusion/saturation; extreme factored-rate safety; separate opportunity-cost availability; and fixed strict improvements over the old coarse AT/W and Augments/W timing grids. Profile-income follow-up checks live in `ProfileGoldChecks.cs`: every phase's override/null/zero/negative rate, reversed same-gear support variants changing the affordability winner, held-lane waits, paid partial/zero-progress starts, no borrowing future-phase income, actual earlier AT funding, refresh-late handoff income, phase-prefix cache gold conservation/replay, same-key changed DTOs across calls, input immutability, validation and exact old frozen-capture equivalence.
