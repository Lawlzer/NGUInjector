## Stage Timing

Plan version 17 has one universal fixed/flexible/AT scheduler, coordinated by production `Main.ProtectedTiming.cs` with the pure `Managers/ProtectedStageScheduler.cs` engine. These retained internal names and the `protected` test selector do not represent an optional user-facing mode. Runtime advertises `stageTimingVersion: 1`, `planVersion: 17`, and `stageOverridesV1: true`; progress uses `schedulerMode: "stages"`, row `timingKind: "fixed"`, `"flexible"`, or `"target"`, and the unchanged root `protectedWorkComplete` durable gate. There is no legacy scheduler or timing fallback.

Run `dotnet run --project checks/ProtectedTiming/ProtectedTimingChecks.csproj` for the source-linked pure engine. Checks cover raw relative weights (including 35/50/15), reservation of every unfinished fixed row, full applied-time credit, slower-clock continuity, offline gaps, strict short-stage completion, AT gates, edits, bounded repeats, manual skip/set/restart, cumulative history, and strict checkpoint restore. The only automatic early finish is a resync of at most 15 seconds for fixed stages longer than 15 seconds, at the expected boundary with fresh positive continuous credit. Stages of 15 seconds or less earn their full duration; selection, first application alone, or an unarmed restore cannot waive work. An explicit manual skip is a recorded waiver, not fabricated training. The horizon uses an enabled positive `TimeTriggerSeconds`, otherwise nonnegative `StageDurationSeconds`; fixed edits do not grow it. Unknown AT duration consumes flexible time, never reserved fixed time.

`ProtectedApplicationChecks` in SustainedFocus executes the real allocator and checks application receipts: unavailable/unmanaged requested work cannot arm credit, while completed targets do not need a positive resource transfer. Its transition checks require a new row's own application, reject stale selections, preserve earned work on invalidation, and keep snapshots inert. Its coordinator boundary is a test stub, not the production persistence path.

After building the production injector and BlackBar executable, append `protected` to run `ProtectedTimingIntegrationChecks` alone. These full-pipeline checks execute the actual production coordinator, sidecar persistence, shared automatic-rebirth readiness, and allocation/application-commit path against data-only game fixtures. Transition checks verify that 10s/4s and 10s/2s rows, loop re-entry, fixed/flex/fixed/AT sequences, and manually selected next rows are **allocated and applied**, not merely selected: each fixed row earns only its own committed intervals and new entries get stable resource/equipment ownership. Failed, locked, and unmanaged applications freeze credit; fight actions run once per actual entry, including loops and edits. Manual-credit fixtures separately isolate checkpoint and gate behavior, so they are not presented as proof of actual allocation.

Integration coverage includes every ANY/ALL time/NUMBER/climb trigger combination waiting for mandatory fixed and AT work unless explicitly skipped, checkpoint durability/failure, same-epoch restore without offline fixed credit, rebirth/save mismatch, corruption, structural deletion, pause/invalidation, zero-funded flex completion, and read-only telemetry. Progress persistence failure keeps automatic rebirth closed even when the in-memory scheduler has completed. The checkpoint's outer coordinator/epoch wrapper remains version **1**, but the nested scheduler core accepts **version 2 only**. New history fields are required; version-1 cores are rejected with no legacy reader and may cause a one-time uncredited restart of mandatory work. Valid version-2 cores restore earned work, cumulative history, entry identity, and explicit skip waivers unarmed. There is no timing mode-flip reset. ExternalUi store checks verify canonical version-17 load/read/save/copy behavior, retained original fixed seconds and budgets, non-writing normalized reads, removal of obsolete `ProtectedStageTiming` regardless of its value, and preservation of checkpoints during that flag cleanup. No running game is accessed.

### Manual Actions And History

The `setPlanStage` command takes exactly `args: { name, expectedRevision, expectedEntry, action, stageIndex }`, with `action` equal to `"skip"`, `"set"`, or `"restart"` and **zero-based** `stageIndex`. Skip/Restart target the current row; Set may target another valid row. The saved revision and current `planProgress.stageEntry` are checked before mutation. A successful command durably records the selection and invalidates old application ownership; actual allocation occurs on the next eligible automation pass. A failed checkpoint rolls back scheduler/history/entry/fight state, leaves the restored core unarmed, preserves the previous durable checkpoint, and cannot leak a deferred override into a later pass.

Production integration checks cover skip without invented credit, forward Set waiving unfinished prior rows, and Restart/backward Set resetting current-and-later pass obligations while retaining cumulative applied seconds, elapsed selected seconds, and visits. They verify durable history/restore, one-based human `LastOverride` text (`lastStageOverride`) despite zero-based API indices, stale entry/revision/name and invalid-target rejection, disabled/paused/focus/prep/boss guards, startup/lease dispatch, ownership-safe accrual, and failed completed-restart rollback. Terminal skip changes the entry token without a new visit or Fight on entry, including after restore; explicit Restart/Set opens one new entry fight. Command success is not itself proof of application: checks run the next automation pass and assert real resource/application ownership.

Read-only history telemetry reports each row's `appliedSeconds`, `elapsedSeconds`, `visits`, and `state` (`current`, `completed`, `skipped`, or `pending`), plus root `stageEntry`, `lastStageOverride`, and `lastStageOverrideAt` (rebirth-clock seconds). Applied time requires continuous verified application/ownership for every kind, including a held final allocation. Elapsed selected time includes offline gaps and is not training credit. Cumulative history survives manual restart/backward Set and loops; pass-level progress/skip flags can reset independently. No earlier row is inferred trained merely from its position. Pure checks also reject version-1 cores and malformed/ghost history metadata transactionally.

Frontend checks cover immediate **Skip current stage**, **Restart current stage**, and **Set as current stage** controls without confirmation popups, retaining stale-entry/revision rejection and pending-action guards. Segment click/tap still only opens settings. Hover/focus and touch-accessible panel details distinguish actual applied from elapsed selected time, visits, and backend state; missing values stay unrecorded. Manual actions are unavailable offline/stale, with dirty or pending edits/actions, unsupported/mismatched telemetry, or an inactive/interrupted plan, with backend guards for prep/boss/focus conflicts. These UI checks do not replace the production full-pipeline application and durability assertions.
