# NGUInjector.UI

Standalone **Tauri 2 / Rust + Svelte 5 / TypeScript** controller. The Unity/Mono automation stays in the injected C# DLL. The app belongs to the existing NGUInjector repository, not the neighboring `temp` checkouts.

## Run

Prerequisites: Node 22.12+ or 24+, Rust stable, Microsoft C++ Build Tools, and WebView2. Bridge regression checks need the .NET 8 SDK/runtime. Building the injector also needs .NET Framework 4.8 targeting tools and the NGU Idle managed assemblies.

From the repository root:

```powershell
.\start-ui.ps1          # Builds the native executable if missing, then opens it
.\start-ui.ps1 -Dev     # Vite + Tauri hot reload
.\start-ui.ps1 -Build   # Rebuild the native executable before opening
.\verify.ps1 -Scope UI
# All offline scopes, including compiled native checks:
.\verify.ps1 -GameFolder "C:\path\to\NGU IDLE"
```

Or from this folder:

```powershell
npm ci
npm run tauri dev
npm run tauri -- build --bundles nsis
```

The native executable is `src-tauri/target/release/nguinjector-ui.exe`; installers are under `src-tauri/target/release/bundle/` after a bundled build. Neither opening the app nor verification starts the game, injects code, or performs live actions.

## Connect

1. Stop/unload any currently injected instance before changing startup mode.
2. Open the controller and use **Enable External UI** on the Dashboard.
3. Build/inject the updated C# DLL through the existing injection workflow. Start the game yourself; do not invoke restart scripts merely to open the controller.
4. The dashboard becomes Connected after successful injector initialization.

The startup marker is `%USERPROFILE%\Desktop\NGUInjector\external-ui.enabled`. Alternatively set `NGUINJECTOR_EXTERNAL_UI=1` in the **game process environment** before launching it. A marker is not proof of connection; the UI requires a fresh heartbeat and `status: running`.

The default path deliberately matches the existing injector, even if Windows redirects the Desktop to OneDrive. The folder picker can select another existing data folder for offline editing; it does not change the injected DLL's runtime path. Remove the marker before a subsequent injection to return to WinForms.

If a refresh cannot read `runtime.json` because another process has it locked (Windows error 32), the UI automatically retries every five seconds until the read succeeds. The retry message clears on recovery, unsaved edits are retained, and writes/game commands are not replayed.

## Features

replacing Fight on entry. Enable Fights in a stage, choose Stage entry or Augments
started, set First fight after, and optionally Repeat every. For fights at 3m and
6m, use a 3m first delay and 3m repeat. Timing edits apply next entry/restart;
turning Fights off stops future admissions. This requires the updated injector's
`fightScheduleVersion: 1` capability; update the UI and injector together.
The schema-17 descriptions below document the preceding timing migration; the
current canonical plan version is 18 with those timing semantics unchanged.

- Injector errors: a full-width alert above navigation on every tab combines startup errors, caught automation errors, explicit execution failures/review blockers, failed commands, and UI read/save failures. Normal waiting, spawn/cooldown, and unverified observations are not alarms. Each error shows its actual context/reason, optional repeat count, and closed Details; Logs and existing selection-review/save-retry controls provide explicit recovery. Nothing is dismissed, applied, or replayed by viewing errors or refreshing. Disconnected/stale telemetry retains reported faults and marks current automation status unknown.

- Blood Magic: current/goal percentages, positive remaining blood, full-magic ETA while Casting or the current status otherwise, unavailable notices, Iron Pill eligibility blockers, and saved reservation thresholds. Recent automatic casts are in Logs; the casting-rules disclosure is removed.
- Global weighted presets: one library shared by Dashboard Quick, Presets, and every plan/stage selector. Fight and Titans remain separate commands.
- Adventure: adventure routing and zones, manual combat options, automatic inventory boosting, and cube Power:Toughness tuning. Each card owns its settings: Farm zone appears only for **Farm selected zone**, shared manual combat options when **Manual adventure** or an enabled manual farm rule is configured, and the cube ratio only when **Auto boost** is enabled. The explicit manual zone requires the manual toggle and remains editable during a push; the latest selection resumes afterward. Boss-only and fallback controls are hidden during a push, retaining their saved values. Turning off Manual adventure enables the game's idle attack once; other enabled manual combat owners can subsequently reclaim it.
- Global adventure rules: the ordered editor in **Adventure automation** edits `_customAdventureRules` (default `[]`, maximum 32). Each record requires exactly `Enabled` (boolean), `MinPower`, `MinToughness`, `MinRegen` (finite numbers >= 0), `Mode` (integer `0` Optimal ITOPOD / `1` idle farm zone / `2` dynamic boosts / `4` manual farm zone), and `Zone` (integer `-1..43` or `1000`, even when unused by that mode). Unknown/missing record keys are rejected. First matching enabled rule wins; all inclusive minimums must pass, and zero means no minimum. Locked zone targets are skipped for modes 1/4; no match uses the existing Adventure mode. Rules are global across plans/rebirths, reevaluate live equipped stats rather than projected gear, and never swap gear. Explicit Manual Adventure overrides rules; titans, quests, fight/rebirth prep, and max push retain higher priority. Manual rules use shared combat options without requiring the manual toggle. Optional `runtime.adventureRules { power, toughness, regen, matchedRuleIndex }` is backend-owned; the index is zero-based, `-1` means none, and older backends may omit it. The UI does not simulate matching. Offline saves fill a missing array with `[]`, preserve unknown surrounding settings, and leave reads/rendering non-mutating.
- Manual Adventure: **Push ITOPOD** is a separate toggle button in this card, not an Adventure mode option. Its saved **Max ITOPOD death limit** appears when push is selected, defaults to `3`, and accepts whole integers `1..1000`. Push can be configured before enabling either Manual adventure or Adventure goal. Changes during a push apply to the next push, without refilling the active budget. Live status shows remaining deaths and floor. Completion returns to the selected manual zone when Manual adventure is enabled, otherwise normal routing resumes with Optimal ITOPOD as the fallback.
- Misc: general automation, resource settings, money-pit gold threshold, Auto use EXP, equipment boost priorities, and a standalone Zone reference with wiki stat recommendations. Equipment loads automatically from live inventory, with one row per owned equipment ID, including disabled gear. An ID is hidden only when every owned copy is level 100 and fully boosted. Select a numbered priority (1 first) or Default, and uncheck Boost to disable an ID; these changes autosave without deleting preferences for hidden or unowned IDs. Explicit priorities override hearts-last but retain existing equipped/locked/auto-merge-slot eligibility. The Auto boost switch and cube ratio remain in Adventure. See [auto-boost](../docs/auto-boost.md). Zone selection is read-only and independent of presets. Blood goals and Iron Pill targets are edited only on Dashboard.
- Plan & Rebirth: auto-rebirth conditions, stage references, reordered stages, loop boundaries, AT targets, and automatic Augments + Wandoos stages. Existing inline stages retain their resource controls; active global preset selection is in Misc, and stored cap buffer is available through Advanced plan JSON.

Drag the whole segment left/right to reorder, or use Alt+Left/Right (Alt+Up/Down also works). There is no separate grip or move button. Each stage has one **Finish stage by** selector: **Fixed duration**, **Flexible share**, or **AT targets**. Fixed stages earn applied training time; flex shares the remaining budget; mandatory AT waits for actual targets and uses wall time from that budget.

Live telemetry never selects a panel, changes the editor plan, or advances the game. Hover, keyboard focus, or touch-opened stage settings expose applied time, elapsed selected time, visits, and state. Explicit manual buttons act immediately without confirmation; stage clicks only open the editor. Other-plan, mismatched, pending-edit, and offline states leave the bar editable but disable manual actions; there is no separate runtime timeline.
- Logs: bounded tails rather than reading an ever-growing log into memory, a read-only rebirth-history table for the selected plan, plus a dedicated Iron Pill section with the last ten successful automatic casts across all plans. Rebirth rows show local timestamp, reason, duration, boss, NUMBER before/after and gain; full records remain available in closed Details disclosures.
- Advanced: collapsed **Advanced plan JSON** and **Plan library** tools, standalone Combat Prep, manual inventory/augment tools, utilities, data-folder setup, Settings JSON, and game data. JSON editing uses validated buffers and conflict checks, preserving exact large numeric values. Plan library retains create/copy/delete and built-in shortcuts without cluttering Plan & Rebirth.

Priority titans/quests pause the push. Lazy ITOPOD Shifter is disabled during the push and its original state/floor inputs are restored on pause or completion. Only fresh adventure death-log events while this push owns the tower spend the death budget, not healing or voluntary Safe Zone trips. Manual combat honors its recovery/precast options on entry, but skips between-fight recovery trips because leaving the tower resets floor progress. `floor` reports the current tower floor while routing there, otherwise the entry floor.

### Global Presets

Dashboard **Quick** lists every saved global preset as a clickable tile. Clicking applies that preset and opens its details below; **Close** only hides details. **Manage presets** opens the full library for adding, cloning, deleting and editing definitions. Changes autosave after a 350 ms pause, with no manual Save step. Dashboard and **Presets** use the same mounted editor, controller-owned library draft and saved baseline, independent of the plan being browsed. Preview, Apply and Equip wait for autosave; invalid values stay local until corrected. Editing/saving and navigation never equip anything; switching tabs or plans retains drafts and previews. Fight/Titans and **Clear quick** remain separate actions.

All ten production objectives have relative weights: Energy NGU, Magic NGU, blood, ITOPOD PP progress, boosts, zone farming, Time Machine, Augments, Wandoos and Advanced Training. **Dynamic adventure**, available through **Add goal**, assigns its full relative weight to the current Adventure activity's output: PP, boosts, or zone farming. Adventure mode and stat rules choose the activity; power, drops, and respawn matter through their effect on that output, not a fixed extra power priority. There is no separate dynamic-preset creation button. **Adventure power**, **Adventure toughness**, **Energy Cap** and **Magic Cap** value immediate stats rather than training gains. Current `Weights` has fourteen positions; older six-, ten- or twelve-entry definitions are accepted and zero-padded. Energy Cap and Magic Cap presets give only their respective cap a positive weight, enable Auto-update and retain current support. A single positive objective is valid. Weights express relative value, not percentages of energy/magic or separate resource budgets. Presets own five AT ratios under **Advanced settings**, plus support mode, digger budget/weights and constraints. NGU target weights come exclusively from Misc global settings.

**Auto-update** (`AutoUpdate`) defaults to true when absent; explicit false is retained. On means **re-optimize on Equip/re-equip**, not a background timer. Allocation refreshes maintain the acquired policy without searching. Saving changes leaves that policy intact and reports that re-equip is required; a new stage entry or restoration after temporary gear use is an equip event. Off reuses a valid policy computed in this injector session; missing/incompatible policies fail explicitly rather than silently optimizing. Use **Preview + Apply setup** to seed a missing policy. Preview is read-only; Apply uses the exact selected preview candidate. Standalone presets do not expire and use a one-hour forecast; scheduled execution uses stage timing, not a stored preset duration.

The runtime folder's `presets.json` is the only editable weighted library. It supports up to 1,024 definitions within 2 MiB, stable IDs, exact-byte SHA-256 revision checks and lossless unknown fields. Connected actions require `globalPresetsVersion: 2`, `globalNguWeightsVersion: 1` and advertised command support. Dashboard Equip/Apply takes ownership only after preflight and pauses the running plan/auto-rebirth; scheduled execution retains its plan ownership. Referenced presets must be reassigned before deletion. Offline editing requires an initialized library and exclusive ownership of `.injector.lock`.

Plans store **Active preset** as `ActivePresetId` under **Gear settings**. Standard stages store a literal global `PresetId` or `@active` to inherit that selection. New stages and ordinary template rows use `@active` and require an explicitly selected saved active preset. Changing a binding preserves timing, completion targets and Fight on entry; retained legacy focus/gear/priority fields are not execution policy for a referenced stage. Existing stages with empty/missing `PresetId` keep their original capped/overflow allocation until explicitly converted by selecting a global preset, even when the plan has an active preset. Automatic Augments + Wandoos is a separate stage execution mode, not a weighted definition.

Migration imports old per-plan `LoadoutPresets` and supported historical goal/stage definitions into the global library using durable collision-safe `MigrationReceipts`. The selected legacy plan's NGU weights migrate once into global settings before retired ratios are removed; imported presets do not own copies. Retained `LoadoutPresets`, `GoalPresets` and `ActiveGoalPresetIndex` are historical provenance, not a second editable preset authority; plan saves reject changes to them except normalization of retired NGU fields. Receipts prevent deleted imports from being resurrected by those arrays. Migration issues identify unsupported rows or rows requiring explicit conversion; resemblance to a standard tuple is not proof of allocation equivalence.

See [weighted loadouts](../docs/loadout-presets.md), [frontend contracts](../docs/frontend-global-presets.md) and [activity models and limits](../docs/preset-activities.md) for execution/safety details.

**Gear goals** select gear/support independently of **Energy priorities** and **Magic priorities**. Resource priorities fund useful caps in order, with only leftovers passed to later activities; zero gear-goal weights do not disable explicitly configured activities. Misc NGU ratios and zero exclusions still apply. Every fresh preset has reviewed fallback chains, and otherwise unused Energy/Magic start with NGUs without adding production goals. A notice at the top of the selected preset explains that case. AT ratios are editable for allocation-only AT as well as an AT gear goal. Reviewed execution requires `resourceLanePrioritiesVersion: 2`; inactive legacy proposals do not activate themselves. Untouched saved built-ins receive only the three priority fields through an exact-match injector migration, while custom edits, explicit priority choices and deleted rows are preserved. Balanced is no longer created in new libraries; saved definitions and plan references are retained.

### Global NGU Allocation

The **NGU weights** editor is directly visible at the top of **Misc**, with all nine energy and seven magic inputs. Changes autosave to global settings and require no selected plan. The separate live allocation display is read-only. Every allocation path uses these weights; plans and presets cannot override them. All ratios accept integers `0..2147483647`; zero excludes a target, including explicit `NGU-n` priorities. For the generic NGU group, positive ratios share resources with redistribution at buffered caps. An all-zero lane skips NGU so later priorities can run. The outer priority chain remains ordered: `WAN, NGU, TM` funds Wandoos before that group, while positive singleton tokens such as `NGU-4, NGU-6` remain ordered rather than weighted.

Runtime `strategy: weighted-ngu-buffered-cap` and `capBasis: last-allocation-pass` describe this NGU sharing. Root `energyWeights`/`magicWeights` and all 9/7 target rows report desired weights; rows include `index`, `name`, `weight`, exact decimal-string `allocated`, and nullable `bufferedCap`/`belowBufferedCap`. `energyAppliedWeights`/`magicAppliedWeights` (arrays or null) and `energyWeightsApplied`/`magicWeightsApplied` distinguish selected from actually applied weights. Blocked/unknown application never implies desired weights took effect; existing spend remains visible. Exact large amounts remain available in tooltips. Switching tabs preserves the selected plan and pending drafts without loading the active plan or saving anything.

Settings now store `_energyNguWeights: int[9]` and `_magicNguWeights: int[7]`; plan version remains 17 without NGU fields. Fresh defaults select energy Adventure Alpha (index 4) and Drop Chance (index 6), and magic Yggdrasil (index 0), at weight 1; others are zero. Existing selected-plan weights migrate once and take precedence over those defaults. Editing requires `runtime.globalNguWeightsVersion: 1`; missing settings are not invented by the frontend. Global changes invalidate previews and cached setups, with running-policy behavior documented in [global NGU weights](../docs/global-ngu-weights.md).

### Stage Presets And Timing

Version 17 uses one universal stage scheduler for every enabled stage plan: fixed applied time, weighted flexible time, and mandatory AT targets. There is no opt-in timing mode, **Protect fixed stages** checkbox, or bulk **Stage timing** conversion. The updated runtime advertises `stageTimingVersion: 1`, `planVersion: 17`, and `stageOverridesV1: true`; plan progress reports `schedulerMode: "stages"` and row `timingKind: "fixed"`, `"flexible"`, or `"target"`. The root `protectedWorkComplete` field keeps its existing name and means mandatory work is durably completed or explicitly skipped, not that a special mode was selected. Reload the rebuilt injector to execute these rules; an older DLL is not an alternative timing mode.

Each stage's **Finish stage by** selector offers **Fixed duration**, **Flexible share**, and **AT targets**. Fixed durations earn time only after successful stage allocation and application commit, with the required lanes managed and primary work available. Selecting a stage is not application and grants no credit. Pending setup, locks, boss fights, focus overrides, pauses, offline time, and unobserved gaps over 15 seconds earn no fixed time. Credit uses the slower of the rebirth and monotonic heartbeat intervals. The only automatic early-finish exception is a resync of at most 15 seconds for a stage longer than 15 seconds: it must reach its expected boundary with fresh positive credit from a continuous applied interval. Stages of 15 seconds or less require their full applied duration. Neither an unstarted stage nor a restored, unarmed stage can waive time just because its wall-clock deadline passed.

Flexible stages divide the time remaining after reserving **all unfinished fixed work**, including later fixed rows. Enter raw **Flexible weight** values such as `35`, `50`, and `15`; each input changes only that row, and read-only labels show 35%, 50%, and 15% of the flexible pool. Weights need not sum to 100; a single flexible row gets 100% regardless of its positive weight. The horizon is `TimeTriggerSeconds` when `TimeTriggerEnabled` is true and the target is positive, otherwise the saved nonnegative `StageDurationSeconds`. Zero is a valid budget. Fixed edits never expand that horizon, even for fixed-only plans. Fixed work may exhaust or overrun it; flex contracts to zero instead of shortening mandatory work. For `NGU flexible -> Augments 15m -> Wandoos 15m` with a 24h target, NGU normally ends at 23:30. On a late return, unfinished fixed stages still receive their applied time and automatic rebirth waits beyond 24h if necessary.

AT targets are untimed mandatory work with unknown duration: completion checks actual Advanced Training levels, never a time estimate. Time spent waiting for AT consumes the available flexible pool without reducing reserved fixed work. Every automatic time, NUMBER, or NUMBER-climb trigger, in either Any or All mode, waits for all fixed work and mandatory AT targets unless explicitly waived by a manual stage skip. Flexible work alone is not a mandatory rebirth gate. Manual rebirth remains an explicit override.

Runtime progress distinguishes credited fixed time from flexible wall-clock time. Flexible durations are assigned dynamically at entry and adjusted on timing edits; future assignments absorb time already spent, so live attribution compares configured seconds/weights rather than requiring assignments to match nominal editor estimates. Row states come from the backend as `current`, `completed`, `skipped`, or `pending`, never from their position before the current row. The display includes remaining fixed seconds and a timing reason. The AT-to-NGU template creates a mandatory AT row followed by flexible NGU and requires a positive horizon.

Stage progress is checkpointed atomically in `stage-progress-<plan hash>.json`, separate from plan revisions. The outer coordinator/save-epoch wrapper remains version **1**, but its nested scheduler core now accepts **version 2 only**, with cumulative applied/elapsed/visit history, skip state, and the last override. There is no legacy core reader. An old version-1 core checkpoint is rejected and may cause a one-time restart of mandatory work uncredited; history is not synthesized. A valid version-2 core restores progress/history unarmed and awards no offline fixed time; flex can expire while offline. Removing the old timing flag does not itself clear checkpoints or cause a mode-flip reset. Recovery checks the rebirth counter, approximate run origin, clock rollback, configuration, and checkpoint structure; mismatch/corruption starts mandatory work uncredited. The game has no immutable save UUID, so arbitrary replacement/branching of saves with identical epoch metadata cannot be identified perfectly. Automatic rebirth fails closed if progress cannot be persisted, even after the in-memory work completes.

Structural changes reset positional execution; same-kind rows retain positional identity, and ordinary duration/weight/cosmetic edits preserve earned work. Changed saves require fresh application before fixed credit resumes. Loops finish their current mandatory pass but do not open another cycle after the horizon or when rebirth triggers are ready. If rebirth is delayed, the last actually selected allocation stays active; unfunded flexible rows are skipped without entry actions.

Backend load/read normalization returns canonical version 17 without rewriting source bytes. Existing fixed `DurationSeconds`, raw flexible `Percent` weights, AT targets, and the saved budget retain their values; display units do not reinterpret fixed seconds. Current built-in/template fixed stages keep their original seconds rather than scaling to the horizon. The obsolete `ProtectedStageTiming` field is ignored and dropped from canonical output/saves whether it was true, false, or absent. That cleanup is not a behavior choice: old plans execute the same universal scheduler, with no legacy timing or scheduler fallback.

### Manual Stage Actions And History

The toolbar has one action: **Restart current stage**, which reopens that row and all later rows in the current pass. Selecting a different stage replaces Restart with **Skip to selected stage**, which jumps forward or backward and continues from there; the panel's **Set as current stage** performs the same jump. Selecting the active stage or closing the selection restores Restart. Clicking/tapping a segment still only opens/closes settings. Moving forward marks unfinished earlier rows skipped; moving backward resets current-pass earned/completed/skipped progress from the chosen row onward. Restart and Set preserve cumulative history and record a new visit; they do not claim the earlier training never happened.

Manual actions submit immediately without a confirmation popup. Tooltips explain that jumping forward bypasses required work and can allow automatic rebirth sooner. Manual controls are disabled offline, on stale/unsupported or mismatched telemetry, for another/paused/disabled plan, with dirty settings/timing/JSON drafts, or while an action is pending. Focus overrides, rebirth preparation/manual rebirth, and boss fighting also block stage actions. Session, revision, and entry guards are checked before submission and by the backend; manual navigation never saves unrelated drafts.

The connected command is `setPlanStage` with exactly `args: { name, expectedRevision, expectedEntry, action, stageIndex }`. `action` is `"skip"`, `"set"`, or `"restart"`; `stageIndex` is **zero-based**, and Skip/Restart must target the current stage. `expectedRevision` is the saved plan's revision and `expectedEntry` is the latest runtime `planProgress.stageEntry` token. Success means the override was checkpointed; allocation changes on the next eligible automation pass and earns no time until actually applied. A failed checkpoint rolls back the override without a deferred skip or success receipt. Terminal skip changes the entry token but creates no visit and no extra Fight on entry; an intentional Restart/Set is a new entry.

Hover or focus a stage for history details; on touch, tap it to read the same details in its settings panel. **Actual applied** (`appliedSeconds`) counts only continuous intervals with successful application and verified ownership, for fixed, flexible, and AT rows, including a held final allocation. **Elapsed selected (including offline)** (`elapsedSeconds`) counts wall/rebirth time while selected, including offline gaps; it is not training credit. `visits` counts selections/re-entries. These cumulative values survive restart/backward Set and loops within the same valid execution history; current-pass progress can reset independently. Missing history is **Not recorded**, not guessed. Neither a prior row nor a `completed`/`skipped` state proves its full configured duration was trained. `lastStageOverride` exposes the core's human-readable `LastOverride` with **one-based** stage numbers, and `lastStageOverrideAt` records rebirth-clock seconds.

### Stage Editing

Automatic stages expose **Adventure weight**: `0` keeps the existing prep setup,
while a positive value blends each phase's primary gear/support goal at 100 with
the configured Misc adventure goal at that weight. This is a relative preference,
not a resource percentage or maximum loss. For example, `15` selects a 100:15 blend.
Prep retains training, phase timing, and equipment ownership; supported idle farming
runs alongside it. See [the runtime contract](../docs/COMBAT_PREP_BACKEND.md#automatic-adventure-weight)
for deferral, safe replanning, and recovery behavior.

Automatic **Augments + Wandoos** stages show **Actual activity time**, not forecast allocations: AT, Augments and Wandoos are always listed, with **Not visited** for recorded inactive zeros; NGU and Background appear only when visited or active. **Now: activity / duration** shows the active activity's accumulated time in the current run. The compact breakdown sits under the live summary, moving into the matching current stage's selected panel to avoid a duplicate. Unavailable, invalid or mismatched telemetry displays **Activity timing not recorded** in automatic stage panels, never invented zeros. The same breakdown is available in Advanced's planner runtime, including its last terminal run.

These are exclusive phase wall-times **including phase setup**, not fixed-stage training credit. Parallel Wandoos/NGU work is attributed to the owning phase, not separately added. Entry preparation and cleanup are excluded, so the activity sum need not equal the total elapsed stage budget. Counters survive replans and freeze at terminal/cleanup. Scope is only the current or last injector run, held in memory: no persistence, offline credit, cross-session totals or cumulative loop/stage history. Stage attribution first passes the existing fresh heartbeat, ordered-stage and reported-revision gate, then requires scheduled ownership, matching plan name, zero-based stage index and exact stage-entry token plus a nonempty run ID. Old/manual runs and previous loop entries are never attached to a new entry; after the scheduler advances, inspect the last-run receipt in Advanced instead.

The additive schema-1 combat-prep fields are `activityTimingScope: "run"`, `activityTimingSemantics: "exclusive-phase-wall-time-including-setup"` and `activityTimes`, always five `{ kind, elapsedSeconds, active }` records in canonical `AT`, `Augments`, `Wandoos`, `NGU`, `Background` order. Seconds must be finite and nonnegative; duplicate/missing/unknown/out-of-order rows, malformed booleans/numbers or multiple active rows invalidate the breakdown. Cleanup, terminal and stale telemetry never shows **Now** or an active timing badge. Rendering/polling issues no game commands.

### Combat Prep Planner

**Advanced > Auto Augments + Wandoos** is a standalone manual planner. Scheduled automatic stages instead use their actual remaining stage budget in the rebirth plan; no separate Misc duration is required. The standalone planner maximizes terminal Augments x Wandoos (A*W) within a fixed total budget of **7200 seconds (2h)** by default, not minimum focus time or global NGU utility, with editable **3% background energy** and **3% background magic**. Boss attack/defense are reported on original gear AND original physical support as one fixed final setup (Mode B), not optimized fight gear or temporary training support. Duration accepts whole seconds `1..86400`; each background percentage accepts finite numbers `0..100`. **15m / 1h / 2h / 24h** shortcuts only edit the local budget and invalidate an existing preview; they never preview or start. These are local planner inputs, not settings patches or saved plan edits. Polling and tab navigation never preview or start automatically. Drafts, the selected alternative, and its preview remain in the controller across tab changes; changing options, data folder, or injector session invalidates the preview token.

**Preview / Refresh preview** is read-only. Alternatives show OS, augment/AT/Wandoos/background times, AT energy split, owned gear and phase allocations/targets, projected augment and Wandoos multipliers, combined A/W multiplier, gold, levels, and boss attack/defense. Each phase's additive `support` shows beard/digger names and IDs, exact string digger levels, individual drain, gross/drain/net gold per second, budget fraction, current/phase policy, and Wandoos support multipliers; an optional `supportVariantKey` identifies the variant. Support **levels** are frozen with no future growth projected, not support **selection**: choices can differ by phase. Current versus dedicated phase support are bounded candidates, not an exhaustive search. The recommendation is best among evaluated candidates, not a global optimum. The total budget includes preparation. Loadouts use currently owned gear. Equivalent time uses each resource lane's dump gains and backend-declared frozen reference focus rate; lanes are not summed. Missing data from older backends is **Unavailable**, never an invented zero; an explicitly empty beard/digger list is **None**. Financials and other large numeric metrics use compact scientific notation, while level strings remain exact.

**Dashboard Quick** uses the global weighted library described above, not this planner or a static tuple-to-focus button map. Its acquired setup has no automatic expiry. Scheduled automatic Augments + Wandoos is a separate stage mode using the remaining total stage budget; this standalone planner retains its own local inputs. Legacy `focusGoal`/augment-estimate APIs retain their separate behavior, but do not define the current Quick editor.

**Start selected** sends only `{ previewId, candidateId }`. It requires an available candidate whose time split matches the requested total, a preview younger than 120 seconds, unchanged options/session, and fresh backend-advertised command support. The backend is authoritative: its token/fingerprint checks can reject a still-young preview if game state changed. Neither Wandoos lane is funded during AT or before any future AT phase. Exact support is pinned and replayed without resizing; all phase gear/support setup consumes the original deadline. The UI does not simulate completion, apply gear, or advance phases.

**Actual runtime progress** displays read-only `runtime.combatPrep` schema 1: status, phase, run ID, elapsed/remaining times, target verification, actual versus projected multipliers and boss stats, reasons, and warnings. Additive `plannedSupport` for the current phase and `actualSupport` observed in game use the same support fields and appear side by side on desktop, stacked on mobile. `supportStatus` and `supportRestoration { status, reason }` report application and cleanup, including skipped restoration and its reason; planned support is never substituted for missing observations. Missing additive fields remain **Unavailable** without rejecting an older schema-1 response. **Cancel active run** always uses the active runtime `runId`, never the selected preview. Busy state lasts only for the command request, not the two-hour run. A submitted Start spends its local preview token before IPC; submitted cancellation is not repeated for that run unless the backend explicitly reports rejection. Timeout/transport errors report an unknown outcome and do not automatically replay actions. Inspect fresh runtime status before another explicit action.

Planned **GPS budget limit** displays the evaluation's validation cap; observed **Share of gross GPS in use** computes actual drain / gross GPS and is unavailable for zero/invalid gross GPS. Observed `budgetFraction: 1` is not 100% usage or the ordinary planning policy. A **restored** outcome records exact verification when the run ended; resumed normal minute rotation may already have changed current support. Owned cleanup restores original active support plus only owned touched inactive levels; foreign edits are retained. See [shared support](../docs/support-core.md) and the separately owned [current live evidence](../docs/PHASE_SUPPORT_LIVE_VERIFICATION.md); this README does not claim a currently verified final game configuration.

The existing `enqueue_command` transport carries exactly `previewCombatPrep { durationSeconds, backgroundEnergyPercent, backgroundMagicPercent }`, `startCombatPrep { previewId, candidateId }`, or `cancelCombatPrep { runId }`. TypeScript and Rust reject extra/missing arguments, invalid ranges/types, and empty or over-128-character IDs. Commands require a fresh identified injector session advertising the requested command; there is no offline fallback. Preview data is read from `result.data.combatPrepPreview` schema 1. Native `protocol.combatPrep.maxPreviewBytes` now advertises the existing **256 KiB (262144-byte)** action-result wire ceiling, matching native `protocol.maxResultBytes`; the general `MAX_RESULT_BYTES` constant stays **64 KiB** for its other contexts. The frontend validates the advertised limit as a positive safe integer no greater than the native overall limit, then bounds the **complete UTF-8 response**, including runtime, envelope, and other fields, not just the preview. Missing feature metadata retains a conservative **64 KiB** fallback (or a smaller advertised overall ceiling); malformed metadata fails closed and never raises that guard. Older native builds advertising 64 KiB remain capped there until rebuilt/reloaded. The backend reserves **252 KiB** for preview data within the **256 KiB** complete-result ceiling. No new C# or game execution logic belongs to the UI.

## Safety And Storage

The injector owns `.injector.lock` for its lifetime. Offline writes require exclusive ownership of that same file, so a stalled heartbeat or a running WinForms injector cannot accidentally authorize direct edits.

Connected writes use a protocol-v3 command queue executed on Unity's main thread. Commands have unique IDs, expiry times, persistent at-most-once claims, and completion results. A timeout cannot undo an action already running; inspect state/results before retrying.

Plan reads are normalized by the C# implementation when connected. Each read includes a SHA-256 `__externalUiRevision` token. Saves compare it at the actual write boundary and reject stale revisions; history updates also change the revision. This token is transport-only, never stored in the plan. Offline legacy plans must be connected to migrate before editing.

Unknown stored fields are preserved. Plan and global-library JSON cross native IPC as text and use lossless parsing so unknown large numbers are not rounded by JavaScript. Settings use key patches; unknown settings keys are retained but cannot be changed by an older injector. Runtime history and migration receipts remain backend-owned; historical plan preset arrays remain provenance, not a parallel editable library.

Built-in plan shortcuts and deletion protection cover only `24hr` (**24h NGU**), `15m-NUMBER-increase` (**15m NUMBER**), `30m-NUMBER-increase` (**30m NUMBER**), and `1h-1m-NUMBER-increase` (**1h1m NUMBER**). Existing `default`, `infinite`, and `1h-3m-rebirth` files remain ordinary plans. Offline deletion of the paused selected plan switches to the existing `24hr` file; if it is missing or unreadable, deletion fails without changing selection or removing the plan. Rust does not create a generic plan under the daily plan's name. Optional plan `RebirthPrepStartSeconds` accepts nonnegative Int32 seconds; optional stage `UseWandoosWhenTimeMachineLocked` accepts booleans. Omission remains omission, and unknown surrounding fields are retained.

Data stays in the existing folder:

```text
settings.json
presets.json
profiles/*.json
custom-plans/*.json
stage-progress-*.json
logs/*
runtime.json
commands/*.json
commands/claimed/*.claimed
command-results/*.json
```

Claim receipts intentionally remain to prevent replay. Do not delete receipts or reuse command IDs while an injector is running. Arbitrary program execution and general filesystem access are not exposed by the bridge.

## Error Telemetry

`src/lib/injector-errors.ts` is a read-only projection, independent of the selected editor plan. Additive `runtime.automationErrors` entries use `{context, message, details, firstSeenAt, lastSeenAt, count}`; the backend bounds/aggregates this history and owns its lifetime. The UI shows its entries until the backend removes them. Unknown entry fields remain available in Details, and absent older fields do not cause errors or settings writes.

The backend retains up to the 16 most recently occurring distinct context/message pairs for the current injector session, within a 32 KiB serialized UTF-8 budget, with exact repeat counts, first/last UTC timestamps, and bounded diagnostic stacks. New injector startup clears this exception history; ordinary success does not imply an earlier exception was repaired. Full stacks remain in `logs/inject.log`. A failing runtime section publishes `available:false`, `status:"error"`, and its actual reason while healthy sections continue to publish. `resourceAllocation.blocked:true` distinguishes a real allocation refusal from an ordinary `Waiting` state.

Active domain failures use the existing `runtime.execution.domains` map: `{[domain]: {state, reason?, waitingReason?, ...}}`. `Failed`, `Error`, `Blocked`, and `NeedsUser` are alarms (case-insensitive); `reason` takes precedence over the existing `waitingReason`. Other states, including `Observed`, `Waiting`, `Quiesced`, and `Uncontrolled`, do not establish a failure. The backend must publish an explicit fault state for active route/gear/native/resource failures rather than relying on `verified:false`, mismatched observations, or a free-form waiting reason. Existing `resourceAllocation.state` `Failed`/`NeedsUser`, active stage `presetStatus`, cleanup recovery, infeasible selected support, and `executionReview.reviewRequired` are also surfaced. Ordinary Iron Pill eligibility blockers are not execution faults.

UI state-read failures remain separate from save/action failures and clear only after a successful state read. Command request failures retain one entry per command (up to 16) for this folder/controller session; only an explicitly successful repeat of that command clears the local entry. Backend failed-command receipts remain visible as historical failures even after other commands succeed. Refresh never retries a write or game action. The existing runtime-file-lock read retry remains unchanged.

When published, `runtime.execution.lifecycle` must be `Running` for ordinary commands; the injector's `status`, `unload`, and `restoreSaveTest` exceptions still require a fresh supported bridge. Older bridges that omit lifecycle retain their existing capability/heartbeat checks. Automatic initial plan/library reads wait through startup or a connected non-running lifecycle without creating command failures. A failed initial plan read stays visible without heartbeat retries; explicit Refresh or a new folder/injector session permits another attempt. Persisted failed receipts are labelled **Earlier command failed**, with their original ID/timestamp in Details, not presented as evidence of a current execution fault. UI preflight cannot eliminate lifecycle changes before Unity executes a queued read; any backend admission change belongs to the injector, including review of the preset migration performed by normalized plan reads.

A matching running plan can show live estimates; pending edits or mismatched goals/spell state hide stale countdowns. Iron Pill status additionally checks its reported plan and threshold values. Cast history is labeled **all plans** and remains global, backend-owned, and read-only.

The dashboard and numeric settings show current/saved bonus goals, remaining blood, and estimated time to each goal assuming all available magic is assigned to the optimal sustainable blood ritual. The WinForms Automation tab shows the same estimates. The read-only `BloodMagicOptimizer.OptimizeBest()` preview selects the best unlocked/affordable ritual with positive net gold using total available magic, current gear bonuses, and gold income; it does not change allocations. Calculations invert the game's bonus formulas and include each enabled spell's share of unspent blood and projected full-magic production, not the current ritual allocation. A 15% Spaghetti goal requires 163,840,000 total invested blood; 100% Counterfeit Gold requires 512,000,000.

Estimates respect each spell's minimum blood per cast and assume the projected all-magic allocation and current auto-spell split stay unchanged. They do not predict spell split changes when another goal finishes, Iron Pill consumption, or rebirths. Paused spells and optimizer failures have explicit statuses rather than misleading countdowns. The UI identifies the chosen ritual by its zero-based index, matching optimizer diagnostics, and shows the full magic budget and projected per-spell production. Pending external UI edits do not change estimates until saved. A rebuilt injector must be loaded to provide the new `runtime.json` telemetry or WinForms labels.

## Iron Pill

The Blood Magic card persists plan `IronPillSaveSeconds` (integer 0..604800) and `IronPillMinWorth` (finite double 0..1e8), inheriting legacy global defaults of 900 seconds and 0 worth when unset. Actual pill worth is the base Power and base Toughness gained each, capped at 100 million (1e8). While eligible, cast when ready and either enabled threshold is reached. Zero disables that threshold; both zero cast immediately when ready. Eligibility uses actual elapsed rebirth time >=3600s and boss stage >=100, plus effective auto blood spells, the active Custom plan resource automation requirements, and the plan's `AutoIronPillEnabled` permission (default true).

Reserve blood while ready or within the saving-time cooldown lookahead; worth-only mode uses a 900s lookahead, not a fixed casting delay. Before entering each saving window, directly spend existing blood on NUMBER once, then pause automatic loot/gold/NUMBER spending. Rituals produce the shared blood pool; there is no separate Iron Pill production target. The temporary magic priority order starts with `RIT`, `TM,RIT` for Time Machine, or `WAN,RIT` for Wandoos/AT Wandoos. Explicit ritual entries are replaced by the sustainable optimizer-selected ritual; other priorities retain their order. Energy, stage gear, stage transitions, AT targets, and saved orders are unaffected. The quick refresh uses the same override, and plan progress remains running. Manual/pre-rebirth preparation, boss push, and ready automatic rebirth preempt reservation.

Outside reservation, the retained legacy Energy NGU stage/focus path (`EnergyFocus=5`, `MagicFocus=6`, `GearGoal=2`) temporarily moves `RIT` before magic NGUs while an enabled Spaghetti or Counterfeit Gold goal is unmet. This describes inline/legacy focus priorities, not a static Dashboard Quick button or global preset mapping. Dedicated Magic NGU, All NGU, other main-focus stages, already blood-first orders, and lists without magic NGUs remain unchanged. Actual game bonuses use the same whole-percent thresholds as the ordinary automatic spells; zero disables a goal. Reaching both enabled goals restores the configured order. This ordinary catch-up requires auto blood spells and magic management, but not Iron Pill or auto-rebirth permission, and does not flush blood to NUMBER. Iron Pill reservation takes precedence and keeps all ordinary spending paused. Progress exposes `bloodGoalsPrioritized` and `bloodGoalsPriorityReason`, with a matching active-row flag; legacy Quick NGU telemetry exposes its effective magic priorities. The dashboard explains active ordinary catch-up without calling the stage interrupted.

After casting or cancellation, ordinary magic priorities and blood spells resume. A successful cast has a 10-second preparation restart guard. The hard preparation deadline is `max(900, saving seconds) + 60` rebirth-clock seconds, including cooldown waiting; timeout or a rejected NUMBER flush restores ordinary operation and waits 900 seconds before retrying. `runtime.ironPill` reports `reservingBlood`, `savedSeconds`, `prepLimitSeconds`, and `retryInSeconds`; `planProgress.bloodReservedForIronPill` and the active row's effective magic priorities report the overlay without changing configured arrays. The controller displays saving/retry state rather than describing a whole-stage takeover.

The dashboard, settings page, and WinForms Blood Spells group show the latest ten successful automatic casts from persisted settings history. The backend owns `_customIronPillHistory`, an array of entries with public fields `CastAtUtc` (UTC string), `WaitSeconds`, `Worth`, and `RebirthSeconds` (doubles). History is read/written explicitly as JSON rather than relying on Unity's serializer, which can silently omit injected custom record arrays. Settings patches retain live backend history even if Unity omits it; reload validates finite, nonnegative times and worth within `0..1e8`. History is read-only and never submitted in user settings patches. Frontend and Rust validation reject history patches, including offline saves. An untouched stale advanced JSON history uses the latest snapshot rather than overwriting it. Casts previously missing from disk are not synthesized from approximate log timestamps.

Backend integration must provide `SavedSettings.CustomIronPillSaveSeconds`, `CustomIronPillMinWorth`, and `CustomIronPillHistory`, normalize/load/copy/persist them with a 1e8 worth limit, reject history edits in C# settings patches, and record only successful automatic casts. The backend must protect manual rebirth/boss-push prep from reservation and persist history without a full WinForms settings reload. The UI does not implement casting, reservation, or history recording. WinForms refreshes only read-only history in its runtime status loop, not the settings editors.
