# Weighted Loadout Presets

Dashboard **Quick**, the **Presets** tab, and plan/stage selectors use one global weighted library in the runtime folder's `presets.json`. Presets own objective weights, AT ratios, support policy and constraints. NGU selection/ratios come only from Misc global settings, independent of the plan open for editing. Plan version remains 17; the runtime advertises `globalPresetsVersion: 2`, `loadoutPresetsVersion: 2` and `globalNguWeightsVersion: 1`. See [global NGU weights](global-ngu-weights.md) for cache invalidation and running-policy reacquisition.

Defaults, ordered objective/beard/digger metadata, and the seventeen new-library seeds are defined in [shared preset definitions](preset-definitions.md). Definition updates never reseed existing libraries or add creation-only policies to legacy normalization defaults. Untouched saved built-ins receive reviewed priorities through a guarded migration; customized presets and existing explicit priority choices are preserved. Balanced is omitted from new defaults, not deleted from saved libraries.

## Workflow

1. Add, clone, rename or delete global presets from Dashboard Quick or Presets. Both use the same editor and revision-aware library draft; save the library before execution. Editing or saving never applies a setup.
2. Set relative outcome weights for Energy NGU, Magic NGU, blood, ITOPOD PP progress, boosts, selected-zone farming, Time Machine, Augments, Wandoos, Advanced Training, Adventure power and Adventure toughness. A single positive weight is a valid preset.
3. Set independent Energy/Magic priorities, optional minimum adventure power/toughness, and support policy. Each reviewed order funds useful caps before passing only leftovers onward. AT ratios are editable when AT is a gear goal or configured Energy activity; NGU weights stay in Misc. Legacy blood-share overrides remain available for objective-only setup scoring; actual reviewed funding follows the order. Presets have no duration: standalone Preview/Equip uses a one-hour forecast, not an expiry. Scheduled acquisition uses remaining stage time (bounded to 1..604800 seconds); untimed AT stages use the remaining plan horizon, falling back to one hour when exhausted. Allocation refresh retains that forecast context until re-equip. Legacy `HorizonSeconds` is ignored and removed on normalization/save.
4. Preview. This captures one consistent game state without swapping gear, changing support, allocating resources or advancing stages.
5. Read the weighted setup's output, comparison with current gear and percentage of full-focus production. The advisory two-phase output appears as another column in the same table, with its schedule and score below. Allocation/route, gear and support details are collapsed. Quick priorities, specialist cards, warnings/notes and preview diagnostics are not rendered.
6. **Equip** computes and applies a fresh setup when Auto-update is on, the default. When off, it replays the last valid policy computed in this injector session without searching; use explicit Preview + Apply to seed a missing policy. Apply setup uses the exact preview candidate and consumes its authorization token. Dashboard execution takes over only after preflight and pauses the running plan/auto-rebirth; scheduled execution retains its plan ownership.

The page keeps setup controls beside results on desktop and stacks them on mobile. Dashboard lists every global preset and supports in-page editing. Support mode, digger budget and Auto/Custom digger weights are directly editable. Less common constraints and allocation ratios are under **Advanced settings**. Fight/Titans remain commands, not pretend production presets.

The global library supports 1,024 entries within a 2 MiB file, with stable IDs, exact-byte SHA-256 conflict protection, and lossless unknown fields. Empty libraries remain empty. Referenced presets cannot be deleted until reassigned. Offline editing requires an initialized library and excludes concurrent injector writes.

`AutoUpdate` means **re-optimize on equip/re-equip**, not a background optimization timer. Resource refreshes maintain the acquired policy without new search. Saving changes leaves that acquired definition intact and reports that re-equip is required. Temporary gear restoration and a new stage entry are equip events. Stale or missing cached policies fail explicitly; off never silently falls back to optimization.

Plans store `ActivePresetId`. Stages store a literal `PresetId`, or `@active` to inherit the plan selection. Timing, mandatory AT targets, entry fights and automatic Augments + Wandoos execution remain stage concerns. Existing per-plan libraries are imported with durable collision-safe receipts. Historical definitions are retained as provenance, not a second editable library. Existing inline stages keep their original capped/overflow behavior until explicitly converted; migration issues explain which rows need review. Newly created stages use global references. See [frontend contracts](frontend-global-presets.md) and [activity modeling limits](preset-activities.md).

## Priorities And Scores

`Weights` has fourteen entries in this order; old six-, ten-, and twelve-entry definitions are accepted and zero-padded:

```text
energyNgu, magicNgu, blood, pp, boosts, zone, timeMachine, augments, wandoos, advancedTraining, adventurePower, adventureToughness, energyCap, magicCap
```

Weights express relative value, not independent resource budgets. Adventure power/toughness value immediate projected stats through gear and support, not AT gains, and do not select a farming route. Training activities share conserved energy and magic; TM/Augments/blood/diggers share gold constraints. PP and regular-zone rewards compete for one adventure route rather than being credited simultaneously. The added activity forecasts are bounded progression proxies; native locks, unsupported states or failed parity checks remain unavailable rather than fabricated.

For example, `[300, 0, 50, 0, 0, 0]` strongly values energy NGU while still valuing blood. It does not reserve 1/7 of energy for blood or imply a 6:1 production ratio. `[100, 100, 0, 30, 0, 0]` values both NGU lanes and some PP farming.

Reviewed resource priorities are separate from these setup goals. The planner first searches gear/support and freezes the route and reference metadata using only the original goals. It then funds the fixed setup using `EnergyPriorities` and `MagicPriorities`, even for activities with zero objective weight. Adding or reordering fallbacks does not select different gear/support. Setup scoring uses affordable provisional activity amounts, with one shared liquid-gold budget; it never borrows future gold. The internal `SetupScore` selects the setup, while public `Score` and `Metrics` describe its actual funded output. If the selected setup cannot satisfy mandatory funding, application blocks rather than choosing replacement gear based on the resource order.

Priority #1 receives only useful, affordable demand; #2 and later receive the remainder. Higher demand reclaims funding from lower priorities on refresh. Misc NGU zero ratios and native locks still exclude targets, and an all-zero NGU group yields to the next activity. Mandatory AT commitments still require their positive goal/ratios and actual allocation. Temporary blood demand prepends `RIT` without changing setup weights; release recomputes the current saved order. Acquired AUG tier, Wandoos OS, support and route remain fixed during refresh, including when an activity is temporarily unfunded. Reviewed presets do not offer the legacy proportional two-phase advisory.

An explicitly configured nonempty resource order controls that resource even without a production goal. Empty orders do not invent NGU allocation: objective-owned resources remain controlled-empty, while a resource with neither objective nor configured activity remains uncontrolled. Old/custom unreviewed definitions keep legacy allocation until explicit review. The UI and native queue require `resourceLanePrioritiesVersion: 2` for reviewed execution, including plan activation.

Each preview normalizes the weights to sum to one and keeps positive per-goal references from the best feasible specialist production. If an active goal lacks a positive specialist reference, a bounded score-only pass evaluates current/specialist gear with compatible already-found support under the original request (including mandatory gates and fixed splits). Only missing/zero references may use positive feasible production from these seeds. References freeze before mixed optimization and remain unchanged through replay/Apply; final mixed winners never define them. Scores sum normalized weight times retained production, not improvement-only utility or bonus-multiplier products. With no positive measured reference, zero output earns zero and later-discovered positive output earns one unit of scoring utility (at most its own weight), never an epsilon-amplified score. This does not invent production or a retained percentage: zero/unavailable references still have null retained ratios. Positive-reference mixed/fresh results can exceed 100%. Missing positively weighted metrics make a score unavailable, not silently ignored or replaced by zero. Valid zero completed NGU levels is distinct from unavailable production. Search is bounded and heuristic, not a proof of global optimality. See [current mixed-focus behavior and evidence](AUTOMATIC_COMBAT_AND_MIXED_FOCUS.md#mixed-focus-presets).

The current-gear baseline remains internal to the preview for relative metrics; it is not rendered as a setup card. It uses the same comparison allocation policy, not measured current production. With planned support it also uses planned support. Removing its card does not change scores, normalization, search or application safety.

The UI distinguishes `n/a` from `Unknown`: ignored zero/unavailable outputs and zero-denominator comparisons are not applicable, including 0-to-0. Positive production from a known zero baseline reads `New`. Genuinely unavailable positively weighted production remains `Unknown` and still blocks a scored Apply. API nulls are unchanged; display rules do not alter scoring.

## Calculations

- Gear search respects owned equipment instances, distinct item IDs, destination slots and offhand factors. Current gear and twelve focus starts seed a bounded mixed search; legacy exact-goal pruning is not reused for these new objectives.
- Resource projections use the shared `ResourceProjection`/`ResourceProjectionCapture` helpers, getter rounding/clamps, potion order and candidate equipment. Actual reclaimable pools exclude retained basic training. A candidate below that retained allocation is infeasible, not merely a zero-energy candidate. More capacity is not treated as instantly filled resource.
- Candidate adventure stats recompute gear-dependent cube softcaps. Respawn is its own gear spec, separate from move cooldown.
- NGU forecasts use the selected track, target and game level ceiling, shared exact integer capped sharing, a five-second allocation lookahead and tick-cost integration. Native NGU auto-advance is captured and fingerprinted. Enabled auto-advance with an unfinished finite, positively weighted target is refused because native transfers into following excluded targets are not modeled. Unlimited (zero) targets remain supported; no player preference is changed. The integrator returns a conservative completed-level estimate within 0.5% of its frozen zero-initial-bar model, or marks production unavailable when it cannot certify that bound. Aggregate levels remain a progression proxy, not interchangeable NGU bonus utility.
- Blood uses unlocked/start-affordable rituals, discrete `50 / ceil(1 / progressPerTick)` completion rates, captured yields and sustainable gold after digger drain. It does not independently spend the gold already assigned to diggers.
- PP uses the game's ITOPOD progress-per-kill getter and repeatable-floor bounds. Native HP/defense data permits conservative minimum-roll comparisons up to four hits; missing enemy data limits search to the existing one-hit range. Purchased AND enabled Lazy ITOPOD constrains candidates to its native shifter-selected floor, with incompatible cached replay rejected before mutation. The preference is never changed; later stats can move that floor. Units are progress/second, not spendable PP/hour. The floor/kill-time model remains a proxy, not a health/death/regen/frame simulation.
- Boost estimates include existing Almanac tables, filtered drops, recycle/boost bonuses, loot caps, rooted loot and hit-count thresholds. Zone farming reports a drop/kill index, not an invented probability for a specific item.
- Two-phase estimates advance NGU levels/targets, recompute phase-two sharing and carry cap-shrunk pools. They charge the configured initial/internal gear/support overhead. Other bonuses and resource refill stay frozen. They are advisory and are not executable schedules.

Current support is the default. Preset capture, support projection and exact application delegate to the [shared support core](support-core.md), also used by Combat Prep. Planned support generates at most 64 deduplicated legal portfolios, alternating full passes and a top-three support beam during gear search, ranked by actual modeled production/route/split outcomes. Explicit beard priorities fix the filtered/capped selection; default selection retains the ordered core prefix and varies optional slots. Explicit digger weights retain eligibility/ranking/proportions with lower total funding alternatives; automatic portfolios also compare specialist/tilted and immediate-only choices. Shared deterministic affordability/backfill enforces purchased levels, unlocks, slots and candidate GPS. Gold-on/off income is computed read-only in native forward order before digger/blood budgeting, never by dividing out an old beard multiplier. Beard effects use unchanged captured levels, preserving native current effective values when activation is unchanged; permanent bonuses remain unless disabled. Future beard levels, bonus feedback and income growth are not forecast.

Each candidate's `support.diggerWeights` contains the chosen raw twelve-entry style indexed by digger ID, including automatic styles; each digger also exposes `weight`. Preview, replay and observed Apply retain this metadata without deriving weights from levels or drain. The support table shows weight, level and gold drain. Current support has no weighting policy, so its array is empty, row weights are null, and the UI shows `n/a`.

## Adventure Data

The tab includes a read-only sourced reference from [`NGUInjector/Data/AdventureZones.json`](../NGUInjector/Data/AdventureZones.json): all 32 regular zones, a separate titan index, recommended stats, selected drops, source links and unknowns. See [adventure-zones.md](adventure-zones.md) for provenance and conflicts.

That wiki reference does **not** silently replace existing runtime zone overrides or the Almanac model. Player recommendations are not enemy HP or guaranteed survival thresholds. Many enemy stats and some drop caps remain unknown. The UI distinguishes reference information from planner inputs. Farming preview/application fails closed while Beast Mode is on because its incoming-damage penalty is not modeled safely; it is never toggled automatically.

## Legacy Inline API

The paragraphs in this section describe the retained inline preview/apply API (`loadoutPresetsVersion: 2`), not global Equip or plan-owned execution. Global commands resolve committed IDs and library revisions before using the same exact-policy preflight. The reusable global cache is separate from the short-lived preview token; cached gear follows exact instances across slot moves and is rejected on incompatible definition/save/gear changes. Global ownership preserves its acquired definition until a real re-equip event and gives protected stage credit only for an observed valid application. Global NGU weight changes invalidate that policy as described above. Pre-mutation readiness waits are retried with bounded backoff; partial application is latched rather than replayed automatically.

`previewLoadoutPreset` accepts only an inline `preset`. `applyLoadoutPreset` additionally requires the returned 32-hex `previewId` and a `candidateKey`. Both read Misc global NGU weights; deprecated lowercase ratio arguments are rejected.

The server retains one preview for up to 120 seconds. Apply validates the exact definition, ratios, equipment instances/stats, material support/unlock state, native auto-advance flag and save/rebirth epoch. It replays the selected cached policy against fresh pools/progress; it does not search a replacement loadout. Complete exact-instance/empty-slot maps and retained-training capacity in intermediate and final swap states are checked through the shared loadout preflight before consuming the token, invalidating application receipts or recalling anything.

After preflight, Apply invalidates equipment-application receipts, clears Quick focus and idle boss push, equips the selected setup, optionally applies support and allocates energy/magic once. Plan, auto-rebirth and manual-adventure settings stay unchanged, including when initially disabled. Stage identity, fight-entry receipt and scheduler history are retained; protected training credit is suspended until the next normal plan pass reconciles gear/support/allocation. Running automation can therefore replace the one-shot setup on its next pass. A weighted farming goal can route adventure once. Both resource-management lanes must be enabled; conflicting preparation, locks and inventory dragging block application. Existing equip behavior also recalls R3. Other manual-focus commands retain their separate pause/confirmation policies.

Planned support goes through shared `PreflightExactSupport` / `ApplyExactSupport` with exact cached beard IDs and decimal Int64 digger levels, not native maximize/resize inputs. The actuator clears diggers before beard changes, verifies levels and fresh affordability before activation, journals partial writes and preserves still-owned pod drafts across native refreshes. Its partial receipt is not rollback; Combat's owned termination cleanup is a separate caller policy and does not turn preset Apply into sustained ownership.

Direct beard application invalidates the normal coordinator's requirement/observation receipt in `finally`, including partial failures, without resetting its independent minute-rotation clock. Blood transfers write exact `long` ritual/idle amounts and refresh the owning ritual controller. Native `BloodMagicController.addMagic(long)` was inspected: allocation itself does not pay gold or change ritual progress; native ticks retain those responsibilities. The human-facing double input parser is not used.

Successful Apply rebuilds its response from the freshly observed equipped/support state. It returns only the observed candidate plus an explicitly named original `run-baseline`, retaining the run's original normalization and baseline metrics. It does not return the old pre-support candidate metrics or imply that the advisory sequence ran.

This is **one-shot application**, not sustained ownership. Other automation and future gear/resource/support changes can supersede it; ordinary beard rotation may change the selection soon afterward. **Last applied** is historical metadata, not a claim that the current setup is still identical. Failures after mutation are explicitly partial applications; there is no promised rollback or automatic retry.

## Limits And Verification

Read-only preparation (capture/search/replay/preflight) uses cooperative operation deadlines, with a 6,000-evaluation search bound and a bounded preview payload. After the final preflight deadline check, a prepared native commit is not interrupted solely because that preparation stopwatch expires. Post-recall observation and exact-policy funding complete their normal validation and allocation verification without a cooperative deadline; no replacement optimizer runs there. Genuine native errors, foreign changes and unknown partial outcomes retain fail-closed behavior. This is not a hard wall-clock execution guarantee. See [the commit-budget fix and evidence](preset-commit-budget.md). The native bridge permits a separately bounded 256 KiB complete action envelope so attached runtime metadata does not invalidate an otherwise valid preview.

Forecasts exclude partial initial NGU bars, resource regeneration, bonus compounding, potion/pill exhaustion, future unlocks and full enemy combat simulation. Challenge forecasts are refused. Current preset resource/NGU/GPS/drop getter comparisons stay exact. Adventure power/toughness alone use a seven-binary32-ULP acceptance policy, reject nonfinite/clamp-crossing discrepancies and warn on accepted differences; this is not bit-identical emulation or a universal error bound. See [native precision checks](../checks/PresetIntegration/README.md#adventure-float-checks). Compilation and offline fixtures do not substitute for live validation; the [latest three mixed Preview/Apply cases](AUTOMATIC_COMBAT_AND_MIXED_FOCUS.md#mixed-previewapply) passed, but their PP/boost rates are forecasts, not long-run measured yields.

From the repository root, use the public offline runner:


Source includes pure preset, numeric-integration and bridge checks; Native builds production and the selected fixture dependencies in one incremental MSBuild invocation and runs separate executables. UI includes desktop/mobile browsers against mocked native IPC, not live Unity actions. Scoped PASS is not the default all-scopes gate or live acceptance. See [Testing And Save Safety](testing.md) for reports, artifact capture and fail-fast source/output ownership; internal helpers are not public entrypoints.

`checks/PresetIntegration/README.md` covers the compiled preset adapter fixture, including real Preview/Apply, native beard activation/digger affordability, native preference invalidation, exact-long allocation and intermediate capacity preflight. It never attaches to or modifies a running game.

### Native Allocation Slot Fix (2026-10-19)

The game's backing collections contain 11 energy NGU slots, 11 magic NGU slots and 10 AT slots, while preset policies address 9, 7 and 5 supported targets respectively. Comparing whole collections with `SequenceEqual` rejected correct allocations after application and prevented acquisition of the preset's sustained ownership receipt. Verification now requires every supported target to match exactly, every trailing native slot to be zero, and enough native slots to contain all policy targets. Unexpected allocations are still rejected rather than ignored.

The compiled native-shape regression reproduced the original allocation-receipt exception against the previous DLL. After a normal Release rebuild, all 72 shape assertions and the full 7,576-assertion preset integration suite passed, including global Equip/refresh with 11-slot NGU collections. For current focused verification, use `.\verify.ps1 -Scope Native -Suite PresetIntegration -Selector '--allocation-shapes'` from the repository root, not an unlocked EXE.

Live verification restarted NGU and the injector, resumed `24hr` at its existing `NGU Energy` stage (index 3), and observed seven fresh runtime samples over 60 seconds. Both NGU lanes remained allocated with a valid scheduled receipt; applied time advanced from 59.65s to 118.65s. The final sample at 02:08:31 local showed 107,502,471 energy in energy NGUs and 4,132,300 magic in magic NGUs, with no active Quick, boss push or combat-preparation owner. Auto-rebirth was left disabled during verification; preset definitions and plan allocation settings were unchanged. Evidence is in the local temporary report directory: `ngu-fix-20261019-summary.json` and `ngu-fix-20261019-sample-{0..6}.json`.
